# RAG Interview Questions

50 detailed RAG questions for senior .NET/Azure AI engineering interviews, Microsoft-centric (Azure AI Search + Azure OpenAI), accurate to mid-2026. Consolidated and de-duplicated from the RAG question banks — every question that appeared across sources is represented here exactly once, with a senior-level answer.

---

**Q1.** What is Retrieval-Augmented Generation and why use it (instead of fine-tuning for knowledge)?

RAG augments an LLM's generation with information retrieved at query time from an external knowledge source (documents, databases, search indexes). Instead of relying solely on the model's parametric memory, you retrieve relevant passages and inject them into the prompt as grounding context, then ask the model to answer using that context. Benefits: (1) **Freshness** — answers reflect up-to-date or private data the model was never trained on; (2) **Grounding/accuracy** — responses cite retrieved evidence, reducing hallucination; (3) **No retraining** — you update the knowledge base, not the model, far cheaper and faster than fine-tuning; (4) **Attribution** — citations build trust and enable verification; (5) **Access control** — you can security-trim retrieval so users only see permitted data. Fine-tuning bakes knowledge into weights that go stale, can't cite sources, and need expensive retraining to update. The trade-off is added retrieval infrastructure and latency, plus dependence on retrieval quality (garbage in, garbage out). RAG is the dominant pattern for enterprise QA over proprietary content; on Azure it's typically Azure AI Search + Azure OpenAI.

**Q2.** Describe the end-to-end RAG pipeline.

Two phases. **Indexing (offline):** ingest source documents (PDFs, Office docs, HTML, DB rows); extract and clean text (often with Azure AI Document Intelligence for complex PDFs); **chunk** into passages; **embed** each chunk with an embedding model (e.g., text-embedding-3-large); store vectors plus text and metadata in a vector/search index (Azure AI Search). **Query (online):** take the user question, optionally rewrite/expand it; embed it; retrieve top-k chunks via vector and/or keyword (hybrid) search; optionally **rerank** (semantic ranker) and filter by metadata/security; assemble the top chunks into a grounded prompt with the question and instructions to answer only from context and cite sources; call the LLM; return the answer with citations. Production adds incremental/freshness indexing, evaluation, caching, monitoring, and guardrails. Quality hinges on chunking, embedding choice, retrieval strategy (hybrid + reranking), and prompt grounding — each a tunable stage.

**Q3.** What chunking strategies exist and how do you choose?

Common strategies: **fixed-size** (split by a token/character count, e.g., 512 tokens) with **overlap** (10–20%) so context isn't severed at boundaries — simple and robust. **Sentence/paragraph-based** splitting respects natural boundaries. **Recursive** splitting tries progressively finer separators (sections → paragraphs → sentences) to keep chunks semantically whole. **Structure-aware** chunking uses document layout (Markdown headings, HTML tags, PDF sections from Document Intelligence) so each chunk is a meaningful unit with heading metadata. **Semantic chunking** groups sentences by embedding similarity so each chunk is topically cohesive. Choose based on content: dense technical docs benefit from structure-aware/semantic chunking; uniform prose works fine with fixed-size+overlap. Consider chunk size vs. the embedding model's optimal input and the LLM's context budget; smaller chunks = precise retrieval but more pieces; larger = more context but noisier and costlier. Always include metadata (source, title, section, URL) for citation and filtering.

**Q4.** What is the right chunk size and overlap?

No universal value — it depends on content and the embedding/LLM. A common, effective default is **300–600 tokens** per chunk with **10–20% overlap** (e.g., 512 tokens, 50–100 token overlap). Smaller chunks (128–256) give more precise retrieval and better citation granularity but fragment context and increase the number of chunks to manage/rerank. Larger chunks (800–1000+) preserve more context per piece (good for narrative or answers spanning paragraphs) but dilute embeddings and waste prompt tokens/cost. Overlap prevents losing information at boundaries — an answer that straddles a split. Tune empirically: build an eval set and measure recall@k and groundedness across sizes. Azure's integrated vectorization defaults often land around 512 tokens with overlap. Align chunk size to the embedding model's recommended input length to avoid truncation.

**Q5.** How do you choose an embedding model?

Pick based on quality, dimensionality/cost, language coverage, and platform fit. On Azure OpenAI, the main choices are **text-embedding-3-large** (highest quality, 3072 dims by default) and **text-embedding-3-small** (cheaper/faster, 1536 dims), plus the older **ada-002** (1536). The `-3` models support **dimension reduction** (e.g., 256/512/1024) to cut storage and search cost with modest quality loss — useful at scale. Consider domain (evaluate on your own data), multilingual needs, max input length (so chunks aren't truncated), and that **query and document embeddings must use the same model**. Higher dimensions improve recall but increase index size and search latency/cost. Benchmark candidates on a labeled retrieval set (recall@k, MRR) rather than trusting leaderboards. For most Azure RAG, text-embedding-3-large (optionally dimension-reduced) is the strong default; -small when cost/latency dominate.

**Q6.** Explain vector search vs. keyword search vs. hybrid search.

**Keyword (lexical/BM25)** matches exact terms — great for product codes, names, acronyms, error codes — but misses synonyms and paraphrases ("car" vs "automobile"). **Vector (semantic)** embeds query and documents and finds nearest neighbors, capturing meaning and paraphrase, but can miss exact rare terms and may retrieve "topically related but wrong" passages. **Hybrid** runs both and fuses results (Azure AI Search uses Reciprocal Rank Fusion to combine BM25 and vector scores), getting semantic recall plus exact-term precision. In practice hybrid consistently beats either alone on real workloads, especially enterprise content full of jargon and identifiers. On Azure AI Search you issue one query with both search text (keyword) and a vector, and RRF merges them; add the **semantic ranker** on top for further gains. The standard Azure recommendation is **hybrid + semantic ranking** as the default retrieval configuration.

**Q7.** What is HNSW and how does Azure AI Search use it?

HNSW (Hierarchical Navigable Small World) is the approximate nearest-neighbor (ANN) algorithm Azure AI Search uses for fast vector search. It builds a multi-layer graph of vectors where upper layers are sparse "express lanes" and lower layers dense; a search starts at the top and greedily navigates toward the query's nearest neighbors, giving sub-linear search time over millions of vectors with high recall. Key tunable parameters in the vector profile: **m** (max bi-directional links per node — higher = better recall, more memory), **efConstruction** (candidate list size during build — higher = better graph quality, slower build), and **efSearch** (candidate list size at query time — higher = better recall, slower query). Azure also offers an exhaustive **exhaustiveKnn** option for exact search on small datasets or ground-truth evaluation. You choose the distance metric (cosine, dotProduct, euclidean) in the profile. HNSW is what makes low-latency semantic retrieval feasible at enterprise scale; tune ef* to balance recall vs. latency.

**Q8.** What is the semantic ranker in Azure AI Search?

The semantic ranker is a second-stage reranker that takes the top results from initial retrieval (BM25/vector/hybrid) and re-scores them using a deep learning model (Microsoft Bing/research lineage) for semantic relevance. It reorders results so the most genuinely relevant passages rise to the top — markedly improving precision and the quality of context fed to the LLM. It also produces **semantic captions** (the most relevant extract from each result) and **semantic answers** (a directly extracted answer span when confident), useful for grounding and citations. Enable it with a semantic configuration on the index and set `query_type="semantic"` (or semantic with hybrid). It reranks up to a limited number of top documents (e.g., 50). It's a billed add-on tier, but the relevance lift for RAG is substantial — the standard advice is hybrid retrieval + semantic ranker. It saves you from running your own reranking model.

**Q9.** What is integrated vectorization in Azure AI Search?

A built-in capability where Azure AI Search handles chunking and embedding for you, at both indexing and query time, so you don't build a separate embedding pipeline. During indexing, an **indexer** with a **skillset** pulls documents from a data source (Blob, ADLS, SQL), cracks/extracts text, applies a **Split skill** (chunking) and an **AzureOpenAIEmbedding skill** (calls your Azure OpenAI embedding deployment) to vectorize chunks, and writes vectors + text + metadata to the index. At query time, a **vectorizer** on the index automatically embeds the incoming query with the same model — so you send plain text and Search vectorizes it server-side. Benefits: less custom code, consistent chunking/embedding, easy incremental indexing via the indexer, and simpler queries. It supports pull-based ingestion and change tracking for freshness. This is the recommended fast path for building Azure RAG indexes and pairs naturally with hybrid + semantic ranking.

**Q10.** How does security trimming work in RAG on Azure AI Search?

Security trimming ensures users only retrieve documents they're authorized to see. The standard approach: store an access-control field on each document/chunk — a collection of group IDs or user IDs (`group_ids`) that may access it. At query time, obtain the caller's identity and group memberships (e.g., Entra ID groups from their token), then add a **filter** restricting results to documents whose `group_ids` intersect the user's groups: `search.in(group_ids, 'g1,g2,g3')`. The index never returns documents outside permissions, so the LLM can't ground on — or leak — unauthorized content. For large/dynamic ACLs, Azure AI Search has added native **document-level access control** integrated with Entra ID and source permissions (SharePoint/ADLS) so trimming stays in sync automatically. Critically, trimming must happen in the retrieval layer, not be left to the model. Essential for enterprise RAG over mixed-permission content, and a frequent design/interview topic.

**Q11.** What is reranking and why does it help?

Reranking reorders an initial candidate set by deeper relevance scoring before passing the top results to the LLM. First-stage retrieval (vector/BM25/hybrid) optimizes for recall and speed over potentially millions of items, returning a broad candidate list that may be imperfectly ordered. A reranker — a **cross-encoder** or semantic model that jointly examines the query and each candidate — produces much more accurate relevance scores, pushing the truly best passages to the top. This matters because the LLM only sees the top few chunks you include; if the best evidence is ranked 8th and you pass top-5, the answer suffers. Reranking improves precision@k, groundedness, and answer quality, and lets you retrieve a wide net cheaply then keep only the best. On Azure, the **semantic ranker** is the managed reranker; you can also use external cross-encoders. The pattern — retrieve broadly, rerank precisely, pass few — is a core RAG quality lever.

**Q12.** What is query rewriting and why is it needed?

Raw user queries are often suboptimal for retrieval: terse, ambiguous, full of pronouns ("what about its pricing?"), conversational, or phrased differently from the documents. Query rewriting transforms the query to improve retrieval. Techniques: **expansion** (add synonyms/related terms), **decontextualization** (resolve "it/that" using chat history into a standalone query), **decomposition** (split a complex question into sub-queries for multi-hop), and **generating multiple variants** to retrieve a broader candidate set then merge. You typically use an LLM. In multi-turn chat RAG, rewriting the follow-up into a self-contained query is essential — otherwise retrieval has no idea what "it" refers to. Azure AI Search has a **query rewriting** feature that generates variants server-side to boost recall. The trade-off is an extra LLM call, so cache and keep it lightweight. Done well, rewriting is one of the highest-impact, lowest-cost retrieval improvements.

**Q13.** Explain HyDE (Hypothetical Document Embeddings).

HyDE improves vector retrieval. The insight: a short query and a relevant document live in somewhat different regions of embedding space, hurting similarity matching. HyDE first asks an LLM to *generate a hypothetical answer/document* for the query — a passage resembling what a relevant document would say — then embeds that hypothetical document (instead of, or in addition to, the raw query) and uses it for vector search. Because the hypothetical document resembles real documents in form and content, its embedding lands nearer the actual relevant passages, improving recall — especially for sparse or zero-shot domains where the query alone retrieves poorly. The hypothetical answer can be factually wrong; that's fine, because you only use its embedding to retrieve real, grounded documents, which the LLM then uses to answer. Costs an extra generation call and latency. HyDE is most useful when straightforward query embeddings underperform; it's one tool among query-rewriting strategies, not always necessary if hybrid + semantic already retrieves well.

**Q14.** What is multi-hop RAG?

Multi-hop RAG answers questions requiring chained evidence across multiple documents or retrieval steps, where a single retrieval can't surface everything. Example: "Which products launched after the CEO's start date?" requires finding the CEO's start date, then products and launch dates — two hops. Approaches: **iterative/agentic retrieval** (retrieve, reason about what's missing, formulate a new query, retrieve again, repeat); **query decomposition** (split into sub-questions, retrieve each, synthesize); and **graph-based RAG** (traverse a knowledge graph). Naturally implemented with an agent (agentic RAG) that has a retrieval tool and loops. Trade-offs: more retrieval/LLM calls (latency, cost) and a need for strong termination so it doesn't loop. Azure AI Search's **agentic retrieval** supports query planning/decomposition for these multi-step questions. Multi-hop is where single-shot RAG breaks down and agentic patterns earn their keep.

**Q15.** How do you ground answers and force citations?

Grounding means the model answers only from retrieved evidence and attributes claims to sources. Techniques: (1) **Prompt instruction** — answer only using provided context, say "I don't know" if absent, cite the source ID per claim. (2) **Tag sources** — include each chunk with a stable identifier (`[doc1]`, title/URL) so the model can cite by reference. (3) Require a **citation format** and parse/validate it, rejecting answers lacking citations. (4) Use **structured outputs** to return answer + list of cited source IDs. (5) Post-hoc **verify** that cited content actually supports the claim (a groundedness check). Azure OpenAI **On Your Data** and AI Search semantic answers/captions provide citation scaffolding automatically. The combination of a strict grounding prompt, source tagging, and a refusal instruction is the core defense against hallucination, and citations let users verify — critical for enterprise trust and compliance.

**Q16.** How do you control hallucination in RAG?

Multi-layered. **Retrieval quality first**: if the right evidence isn't retrieved, the model invents — use hybrid + semantic reranking and good chunking to maximize recall of correct passages. **Strict grounding prompt**: answer only from context, explicitly say "I don't know" when evidence is absent, cite sources. **Lower temperature** to reduce drift. **Citation enforcement and verification**: require citations and run a groundedness check (does the cited text support the claim?), rejecting or flagging unsupported answers. **Confidence thresholds**: if top retrieval scores are low, refuse or escalate. **Limit context to relevant chunks** (reranking) so the model isn't distracted by noise. **Evaluate groundedness** continuously (RAGAS-style faithfulness, Azure AI Foundry groundedness evaluator) and monitor in production. **Guardrails/content filters** as a backstop. No single trick eliminates hallucination; the reliable approach is high-recall grounded retrieval + strict prompting + citation/groundedness verification + ongoing evaluation.

**Q17.** What metadata should you store with chunks and why?

Metadata that supports filtering, citation, freshness, and security. Typical fields: **source identifiers** (document ID, file name, URL, page/section/heading) for citations and navigation; **title** for context; **timestamps** (created/modified/ingested) for freshness filtering and ranking; **author/owner**; **content type/category/tags** for filtered retrieval; **language**; **access control** fields (group/user IDs) for security trimming; **version** for handling revisions; and the **parent document ID** to group chunks or expand context. This enables **filtered search**, **security trimming**, **citation rendering**, **freshness boosting**, and **deduplication/versioning**. In Azure AI Search you define these as fields with appropriate attributes (`filterable`, `sortable`, `retrievable`, `searchable`). Rich, accurate metadata is often the difference between a toy RAG and a production one — it lets you constrain and contextualize retrieval rather than relying on embeddings alone.

**Q18.** How does metadata filtering interact with vector search (pre-filter vs post-filter)?

Filtering restricts which documents are eligible before or during vector search — e.g., `category eq 'finance'`, `effective_date ge 2025-01-01`, or security-trimming filters. Azure AI Search applies filters with vector queries in two modes: **pre-filter** (apply the filter first, then run ANN over the qualifying subset) or **post-filter** (run ANN, then filter results). Pre-filtering ensures top-k *within* the allowed set — better recall for narrow filters — but can be costlier; post-filtering is cheaper but may return fewer than k after filtering if the ANN top-k didn't include enough matching docs. Azure exposes `vectorFilterMode` (`preFilter`/`postFilter`). Filtering is essential for security trimming, multi-tenant isolation, freshness windows, and scoping by type. Make fields `filterable` and prefer **pre-filter** for selective/security-critical filters so you don't miss relevant authorized documents. Semantic relevance + precise metadata constraints is core to enterprise RAG correctness.

**Q19.** How do you handle freshness and incremental indexing?

Knowledge changes, so the index must stay current without full rebuilds. Use **incremental indexing**: only process new/changed/deleted documents. In Azure AI Search, **indexers** with **change detection** (Blob LastModified/metadata, SQL change tracking, ADLS) automatically pick up deltas on a schedule, re-chunk and re-embed only changed docs (with integrated vectorization), and apply deletions via a soft-delete/deletion-detection policy. For push-based ingestion, track document versions and upsert/remove affected chunks (key chunks by stable IDs from source + chunk index so updates replace cleanly). Handle **deletes** explicitly so stale content can't be retrieved. To bias toward recent content, store timestamps and either filter to a freshness window or boost recency in ranking (scoring profiles). For high-churn data, schedule frequent or event-driven indexing. Monitor indexer runs for failures. Goals: low-latency propagation of changes, no stale/orphaned chunks, and the ability to prefer current information — without re-embedding the whole corpus each time.

**Q20.** What is "On Your Data" in Azure OpenAI?

A built-in feature that connects a data source (most commonly an Azure AI Search index, also Blob) directly to the chat completions API so the service performs RAG for you — retrieving relevant chunks and grounding the answer with citations — without writing the full retrieval/orchestration pipeline. You configure the data source (index, fields, query type like hybrid+semantic, top-k, strictness) in the request or the Foundry playground, and the API returns an answer plus **citations** via a `data_sources` parameter. It supports the recommended retrieval modes (vector, hybrid, semantic) and can use integrated vectorization. Benefits: fast time-to-value, managed grounding and citation handling, consistent API. Limits: less control than a custom pipeline (custom reranking, complex multi-hop, bespoke prompt engineering), so advanced needs graduate to a hand-built RAG with AI Search + Azure OpenAI. Excellent starting point with a graceful path to custom RAG when requirements grow.

**Q21.** How do you evaluate retrieval quality (recall@k, MRR, precision@k)?

You need a labeled set of queries each mapped to the relevant chunk(s)/document(s). **Recall@k**: fraction of queries for which a relevant document appears in the top-k — the dominant RAG metric, since the LLM can only use what's retrieved. **Precision@k**: fraction of the top-k that are relevant — measures noise in the context. **MRR (Mean Reciprocal Rank)**: average of 1/rank of the first relevant result — rewards putting a relevant item high, important because earlier chunks influence the LLM more. **NDCG** accounts for graded relevance and position. Compute these across chunk sizes, embedding models, and retrieval modes (vector vs hybrid vs hybrid+semantic) to choose configurations empirically. High recall@k is necessary; reranking then improves MRR/precision@k. Build this harness early — retrieval is the foundation, and "the LLM is wrong" is frequently a retrieval (recall) failure, not a generation one.

**Q22.** How do you evaluate generation quality (groundedness, relevance, RAGAS)?

Beyond retrieval, evaluate the generated answer. Key dimensions: **Groundedness/Faithfulness** — are all claims supported by retrieved context (no hallucination)? **Answer relevance** — does it address the question? **Context relevance/precision** — were retrieved chunks relevant? **Context recall** — did retrieval capture all info needed for the ground-truth answer? **Completeness/correctness** vs. a reference. The **RAGAS** framework formalizes faithfulness, answer relevancy, context precision, and context recall, typically using an LLM-as-judge to score each. On Azure, **Azure AI Foundry evaluation** provides built-in evaluators (groundedness, relevance, coherence, fluency, similarity, plus retrieval and safety) you can run on datasets and wire into CI/CD. Use LLM-as-judge with clear rubrics, validate the judge against human labels, and track metrics over time to catch regressions when you change prompts, models, chunking, or retrieval. Retrieval metrics (recall@k/MRR) + generation metrics (groundedness/relevance) give a complete picture.

**Q23.** When should you use RAG vs. fine-tuning?

**RAG** is for injecting **knowledge** — facts, documents, up-to-date or proprietary information the model should reason over. It's cheap to update (re-index, no retraining), provides citations/grounding, and handles changing data. **Fine-tuning** is for teaching **behavior/form** — a specific style, format, tone, domain vocabulary, structured-output pattern — or for compressing many-shot prompt instructions into the weights to cut prompt size/latency. Fine-tuning does *not* reliably add new factual knowledge and risks stale/incorrect facts and forgetting; it needs curated training data and retraining to update. Rule of thumb: **RAG for "what the model needs to know," fine-tuning for "how the model should respond."** They're complementary — fine-tune for a domain's style, RAG for its facts. Most enterprise QA needs RAG, not fine-tuning. Start with RAG + good prompting; reach for fine-tuning only for a persistent behavioral/format need prompting and few-shot can't meet efficiently. Cost and maintenance favor RAG for knowledge.

**Q24.** What is agentic RAG?

Agentic RAG puts an LLM agent in control of the retrieval process rather than running a fixed retrieve-then-generate pipeline. The agent can decide *whether* retrieval is needed, *reformulate* the query, issue *multiple* searches, perform *multi-hop* reasoning, choose among *multiple tools/sources* (different indexes, web, databases), and *self-critique* whether it has enough evidence before answering. This handles complex, ambiguous, or multi-step questions that single-shot RAG fails on. Implemented with an agent framework (AutoGen/Microsoft Agent Framework) exposing retrieval as a tool, with strong termination to bound loops. Azure AI Search added native **agentic retrieval**: an LLM plans/decomposes a query into subqueries, runs them in parallel, and merges results — agentic behavior inside the search service. Trade-offs: more LLM/retrieval calls (latency, cost) and complexity, so reserve it for genuinely hard queries; simple FAQ questions don't need it. Agentic RAG is the convergence of the RAG and agent worlds.

**Q25.** How do you optimize RAG latency?

Latency comes from embedding the query, retrieval, optional reranking/rewriting, and generation. Optimizations: (1) **Skip unnecessary stages** — gate HyDE/rewrite/multi-hop. (2) **Tune ANN params** (efSearch) for recall/latency and keep dimensions reasonable (dimension reduction). (3) **Cache** — embeddings of repeated queries, full answers for common questions (semantic cache), and **prompt caching** for the static system prompt. (4) **Parallelize** — keyword and vector retrieval run concurrently (Azure does this in hybrid); parallelize multi-query/multi-hop. (5) **Limit context** — rerank and pass only the top few chunks to cut generation tokens and time. (6) **Stream** the generation so the user sees output immediately. (7) **Right-size the model** — a smaller/faster one where quality allows. (8) Co-locate Search and OpenAI in the same region to cut network hops. (9) Use **PTUs** for predictable low-latency generation under load. Measure each stage to find the bottleneck; output length usually dominates.

**Q26.** How do you optimize RAG cost?

Costs: embedding (indexing + per-query), search service tier, reranking (semantic ranker is billed), and generation tokens (usually dominant). Levers: (1) **Reduce generation tokens** — rerank and pass only the best few chunks; trim chunk size; concise prompts; cap output length. (2) **Right-size models** — cheaper chat model (gpt-4o-mini) when quality permits; text-embedding-3-small / dimension reduction for embeddings. (3) **Cache** — answer caching for repeats, prompt caching for the static system prompt (Azure discounts cached input tokens significantly). (4) **Index efficiency** — dimension reduction shrinks vector storage; right-size the Search tier and replicas. (5) **Batch** embeddings during indexing (Azure OpenAI Batch API offers discounted async processing). (6) **Avoid over-retrieval and unnecessary LLM calls** (don't always run rewrite/HyDE/multi-hop). (7) For steady high volume, **PTUs** can be cheaper than PAYG. (8) Monitor token spend by feature via telemetry and optimize the biggest line items. Cost optimization is mostly about generation tokens and avoiding redundant LLM calls.

**Q27.** What causes "lost in the middle" and how do you mitigate it?

"Lost in the middle" is the finding that LLMs attend best to information at the **beginning and end** of a long context and can overlook relevant content in the **middle**, degrading answer quality as you stuff more chunks in. Mitigations: (1) **Rerank and pass fewer, better chunks** — don't dump 20 passages; pass the top 3–5 most relevant. (2) **Order by relevance** and consider placing the most important chunk first or last (some pipelines reorder so top results bracket the context). (3) **Keep total context tight** — precision beats volume. (4) **Compress/summarize** retrieved chunks before generation if many are needed. (5) Use **higher-quality retrieval** (hybrid + semantic ranker) so you don't over-retrieve to compensate. (6) For very large needs, do **multi-step** retrieval/synthesis rather than one giant prompt. The practical lesson: aggressive reranking and a small, well-ordered context usually beat large contexts, improving both quality and cost.

**Q28.** How do you handle tables, images, and complex PDFs in RAG?

Complex documents lose meaning under naive text extraction (tables flatten, layout/reading order breaks, images carry information). Use **Azure AI Document Intelligence** (Layout/Read models) to extract structured content — tables as structured rows, headings, reading order, key-value pairs — often output as Markdown so structure-aware chunking keeps tables and sections intact. For **tables**, preserve them as Markdown/HTML in the chunk so the model can read them; consider one-chunk-per-table with descriptive metadata. For **images/diagrams**, either generate text descriptions (via a vision model) to embed and index, or use **multi-modal embeddings** so images are retrievable, or store the image and pass it to a vision-capable model (gpt-4o) at answer time. For scanned docs, OCR first. The principle: extract faithfully, preserve structure, represent non-text content as something retrievable and groundable. This dramatically improves RAG on real enterprise documents (financial reports, manuals, forms) versus dumping raw extracted text.

**Q29.** What is the parent-child / small-to-big chunking pattern?

This decouples the chunk you *retrieve on* from the chunk you *pass to the LLM*. You index **small** chunks (precise, focused passages that embed well and match queries accurately) but link each to a **larger parent** (the surrounding section or document). At query time you retrieve via the small chunks for precision, then expand to and pass the **parent** (or a window around the match) for fuller context. This solves the tension between retrieval precision (favors small chunks) and answer context (favors large chunks). Variants: **sentence-window** retrieval (match a sentence, return surrounding sentences) and **auto-merging** (if many child chunks of the same parent are retrieved, merge into the parent). Implement by storing a `parent_id` on each child and fetching parents after retrieval. The result: accurate matching plus sufficient context for grounded answers, often improving both retrieval metrics and answer quality without simply enlarging all chunks.

**Q30.** How do you build conversational (multi-turn) RAG?

In chat, follow-ups depend on prior turns ("what about its warranty?"), so naive retrieval on the raw follow-up fails. Core technique: **query reformulation/condensation** — use the conversation history to rewrite the follow-up into a standalone, self-contained query before retrieving (resolve pronouns and implied subjects). Then run normal retrieval (hybrid + semantic) on the rewritten query, ground the answer, and maintain citations. Manage **conversation context**: include recent turns in the generation prompt but don't let history grow unbounded — summarize older turns and rely on retrieval for facts rather than stuffing all history. Decide per-turn whether retrieval is even needed (a "thanks" doesn't need a search). Persist session state, and security-trim every retrieval by the user's identity throughout. Azure OpenAI On Your Data handles much of this (query rewriting and grounding across turns). The key insight: the standalone-query rewrite step is what makes multi-turn RAG actually work.

**Q31.** What scoring profiles and boosting does Azure AI Search offer?

Scoring profiles customize relevance ranking beyond the default by **boosting** documents based on field values — boost newer documents (freshness), boost by popularity/rating, boost title matches over body, or boost by tag/category. You define functions (magnitude, freshness, distance, tag) and weights in the index's scoring profiles, then apply a profile at query time. For RAG this biases retrieval toward recent or authoritative content without hard filtering — e.g., a freshness function so the model grounds on current policy versions. Term boosting (field weights) helps when title/heading matches should outrank incidental body matches. Note scoring profiles primarily affect keyword/BM25 scoring; with hybrid + semantic ranking the semantic reranker is the dominant signal, but profiles still shape the lexical component and candidate ordering. Use them to encode business priorities (recency, authority, source preference) into retrieval ranking.

**Q32.** How do you choose top-k and reranking depth?

Two knobs: how many candidates to **retrieve** (first-stage k) and how many to **pass to the LLM** after reranking (final k). Retrieve a **broad** first-stage set (e.g., top 30–50) so the reranker has enough good candidates — too small and the best passage never enters the funnel. Then **rerank** that set (Azure semantic ranker reranks up to ~50) and pass only the **top few** (commonly 3–5) to the LLM. Passing more isn't better: it adds cost, latency, "lost in the middle" risk, and noise that can mislead the model. Tune empirically with your eval set: increase first-stage k until recall@k plateaus, then minimize final k while maintaining groundedness/answer quality. For multi-hop/agentic flows, k may vary per sub-query. The recipe — **retrieve wide, rerank, pass narrow** — balances recall against precision and cost. Default starting point: retrieve 30–50, semantic rerank, pass top 3–5.

**Q33.** How do you handle "no answer" / out-of-scope queries?

The system must gracefully refuse rather than hallucinate when the knowledge base lacks the answer or the query is out of scope. Techniques: (1) **Confidence thresholding** — if top retrieval scores (reranker score) are below a threshold, treat it as "no relevant content found" and say you don't know. (2) **Grounding instruction** — prompt the model to answer only from context and explicitly say it can't find the answer otherwise. (3) **Scope/intent classification** — detect off-topic requests and route to a fallback ("I can only help with HR policies"). (4) **Strictness setting** — On Your Data exposes a strictness parameter controlling how aggressively it requires strong grounding. (5) **Citation requirement** — if no sources can be cited, don't answer. (6) **Fallback action** — escalate to a human or suggest contacting support. Handling "no answer" well is crucial for trust: a confidently wrong answer is worse than an honest "I don't know," and it's a common eval/safety criterion.

**Q34.** What is the difference between dense, sparse, and hybrid retrieval?

**Dense** retrieval uses neural embeddings (dense vectors) and nearest-neighbor search to match by meaning — strong on paraphrase/semantics, weaker on rare exact terms. **Sparse** retrieval represents text as high-dimensional sparse vectors over the vocabulary — classic **BM25/keyword** is sparse, and **learned sparse** models (e.g., SPLADE) predict term weights/expansions, combining lexical precision with semantic expansion while remaining interpretable and exact-match-friendly. **Hybrid** combines dense and sparse (or dense + BM25) and fuses the result lists, typically via **Reciprocal Rank Fusion**, capturing both semantic recall and exact-term precision. In Azure AI Search, hybrid = BM25 (sparse/lexical) + vector (dense), fused by RRF, optionally reranked by the semantic ranker. Practical takeaway: dense alone misses exact identifiers; sparse alone misses paraphrase; hybrid robustly handles enterprise content full of both natural language and codes/jargon — hence the standard Azure recommendation of hybrid (plus semantic reranking) as the default.

**Q35.** How do you do deduplication and handle near-duplicate chunks?

Duplicate/near-duplicate content (boilerplate, repeated headers/footers, multiple versions) wastes context, biases retrieval, and crowds out diverse evidence. Mitigations: at **indexing**, deduplicate exact/near-exact chunks (hash content, or detect high embedding similarity) and strip repetitive boilerplate before chunking. Use **stable keys** so re-indexing a changed document replaces rather than duplicates its chunks, and remove old versions on update. At **retrieval/post-processing**, apply **diversity** techniques — e.g., **Maximal Marginal Relevance (MMR)**, balancing relevance against novelty so you don't pass five near-identical passages — and collapse chunks from the same parent. For versioned documents, store a version field and filter to the current version (or boost it via a scoring profile) so stale duplicates aren't retrieved. The goal is a context window of *distinct, relevant* evidence: dedup at index time prevents bloat, MMR/diversity at query time ensures the few chunks you pass cover different facets.

**Q36.** What is GraphRAG?

GraphRAG (notably from Microsoft Research) builds a **knowledge graph** from your corpus instead of (or in addition to) a flat vector index. During indexing, an LLM extracts **entities and relationships** and constructs a graph, then **community detection** clusters related entities and the LLM generates **summaries** for each community at multiple levels. At query time, GraphRAG answers **global/holistic questions** ("what are the main themes across all reports?") by traversing community summaries, and **multi-hop** questions by following relationships across entities — things vector RAG, which retrieves isolated chunks, struggles with. Strengths: connecting dispersed information, reasoning over relationships, whole-corpus sensemaking. Costs: expensive, LLM-heavy indexing to build/summarize the graph, and added complexity. Use GraphRAG when questions require synthesizing across many documents or following entity relationships; use standard vector/hybrid RAG for typical "find the relevant passage" lookups. They can be combined (graph for structure, vectors for passages). An advanced pattern worth knowing for complex enterprise knowledge bases.

**Q37.** How do you ingest from SharePoint / enterprise sources securely?

Enterprise RAG usually pulls from SharePoint, OneDrive, ADLS, Blob, or databases, and must preserve permissions and freshness. Approach: use a **pull-based indexer/connector** (Azure AI Search indexers, or a Logic App/Graph-based pipeline) to ingest documents, with **change detection** for incremental updates and deletion handling. Authenticate with **managed identity** and least-privilege access. Crucially, capture **source permissions** (the SharePoint/ADLS ACLs — which Entra groups/users can access each item) and store them on chunks for **security trimming**, so retrieval honors the same access control as the source; Azure AI Search has native document-level access control that syncs source permissions and trims by the caller's Entra identity automatically. Handle sensitive data (PII) per policy, and ensure deletions/permission changes propagate promptly so revoked content isn't retrievable. Keep data in-region for residency. The hard part isn't ingestion but faithfully mirroring source security into the index so RAG never leaks documents a user couldn't otherwise see.

**Q38.** How do embeddings dimensionality and distance metric affect results?

**Dimensionality**: higher-dimensional embeddings (e.g., 3072 for text-embedding-3-large) generally capture more nuance and improve recall, but cost more storage, memory, and search time, and increase index size. The `-3` models support **Matryoshka-style dimension reduction** — truncate to 1024/512/256 dims, trading a small quality drop for big storage/latency savings, which matters at scale. **Distance metric** must match how the embeddings were trained: OpenAI embeddings are normalized and designed for **cosine similarity** (equivalently dot product on normalized vectors); using the wrong metric (e.g., Euclidean) degrades relevance. In Azure AI Search you set the metric (`cosine`, `dotProduct`, `euclidean`) in the vector profile — use **cosine** for Azure OpenAI embeddings. Query and document embeddings must use the **same model and dimensionality**. Practically: pick text-embedding-3-large with cosine; consider dimension reduction if storage/latency is a concern; and validate recall@k after any dimensionality change rather than assuming the trade-off is acceptable.

**Q39.** What is Reciprocal Rank Fusion (RRF)?

RRF is the algorithm Azure AI Search uses to **merge** the result lists from hybrid search (BM25/keyword and vector) into a single ranking, without needing to normalize their incompatible score scales. For each document, RRF sums contributions of `1/(k + rank)` across each result list it appears in (where `rank` is its position and `k` is a constant, commonly 60). A document ranked highly in either list gets a strong contribution; documents appearing high in *both* lists rise to the top. Because it uses **ranks, not raw scores**, RRF sidesteps the problem that BM25 scores and cosine similarities aren't directly comparable. It's simple, robust, and effective — which is why it's the default fusion for Azure hybrid search. The semantic ranker can then rerank the fused top results for final precision. Understanding RRF explains *why* hybrid works without score calibration and why a document strong on both lexical and semantic signals tends to win.

**Q40.** How do you keep RAG answers within data residency / compliance boundaries?

For regulated data, ensure it stays in approved regions and is handled per policy. Deploy **Azure OpenAI and Azure AI Search in the required region(s)** so prompts, embeddings, and indexed content don't leave the residency boundary; Azure OpenAI processes data in the deployed region and (with abuse-monitoring opt-out where granted) doesn't store prompts/completions beyond transient processing, and customer data is **not used to train** the foundation models. Use **Private Endpoints/VNet** so traffic stays on the Microsoft backbone, **managed identity + RBAC** for access, and **Key Vault** for any secrets. Apply **security trimming** so users see only permitted data, and handle **PII** (mask/redact or restrict) per policy. Maintain **audit logging** of queries and retrieved sources. Respect retention and **deletion** — when source data is deleted, remove its chunks. For multi-region services, pin data flows to compliant regions and document the data flow for compliance reviews. Regional deployment + private networking + identity-based access + trimming + audit is the standard compliant RAG posture on Azure.

**Q41.** How do you A/B test or compare RAG configurations?

Treat RAG config (chunk size/overlap, embedding model/dimensions, retrieval mode, top-k, reranking, prompt) as experiments evaluated on a **fixed labeled dataset** of representative queries with known relevant docs and/or reference answers. For each configuration, run the **offline eval harness** computing retrieval metrics (recall@k, MRR, precision@k) and generation metrics (groundedness, answer relevance/correctness via LLM-as-judge or human). Change **one variable at a time** to attribute effects, and report metric deltas with the dataset held constant. For production validation, run **online A/B tests**: split live traffic between configurations and compare user signals (thumbs up/down, follow-up rate, deflection, task success) and operational metrics (latency, cost). Use the offline harness in **CI** to catch regressions before deploy. Azure AI Foundry's evaluation tooling supports running evaluators over datasets and comparing runs. The discipline of an evaluation dataset plus controlled, one-variable-at-a-time comparison is what turns RAG tuning from guesswork into engineering.

**Q42.** What guardrails and safety apply specifically to RAG?

RAG-specific safety spans inputs, retrieval, and outputs. **Inputs**: detect prompt-injection — malicious instructions hidden in retrieved documents ("ignore previous instructions...") are a major RAG threat, since you feed external content into the prompt; mitigate with input/content filtering, **spotlighting/delimiting** retrieved content as data (not instructions), and instructing the model to treat context as untrusted. **Retrieval**: enforce **security trimming** so users can't retrieve unauthorized data, and avoid surfacing PII/sensitive content beyond policy. **Outputs**: apply **content filters** (Azure AI Content Safety / Azure OpenAI filters) to block harmful generations, enforce **grounding** and citation so answers don't hallucinate, and verify **groundedness** (Azure groundedness detection). Also guard against **data exfiltration** via crafted queries and against leaking system prompts. Log and monitor for abuse. The standout RAG risk interviewers probe is **indirect prompt injection through retrieved content** — knowing to delimit/spotlight untrusted context and never let it override instructions is a strong signal.

**Q43.** How do you cite sources accurately and avoid mis-citation?

Accurate citation requires each claim to map to the source that actually supports it. Techniques: (1) **Tag each chunk** with a stable, unique reference (`[doc1]` plus title/URL/page) in the prompt and instruct the model to cite the specific reference(s) for each statement. (2) Prefer **structured outputs**: have the model return claims with associated source IDs, so citations are parseable, not free-text. (3) **Verify** citations post-hoc — check that the cited chunk's text entails the claim (a groundedness/NLI check), flagging or dropping unsupported citations. (4) Use Azure features providing **citation scaffolding**: On Your Data returns citations to documents it used; semantic ranker provides captions/answer spans. (5) Keep **passed context small and relevant** (rerank) so the model isn't tempted to cite the wrong nearby chunk. (6) Render citations as **clickable links** to the source. Mis-citation usually stems from too much undifferentiated context or free-text citing; tagging + verification + tight context fixes most cases.

**Q44.** How do you handle very large documents that exceed context?

You can't pass a 200-page manual into the prompt, so you chunk and retrieve — but large/structured documents need care. Use **structure-aware chunking** (split on sections/headings via Document Intelligence) so chunks are meaningful, and attach hierarchical metadata (document → section → chunk) for context and citation. Use the **parent-child / small-to-big** pattern: retrieve precise small chunks but pass the surrounding parent section for context. For questions needing **whole-document** understanding (summaries, "does this contract contain X anywhere?"), single-shot retrieval is insufficient — use **map-reduce summarization** (summarize chunks, then the summaries), **iterative/agentic** passes, or **GraphRAG** for cross-document synthesis. For long-context models you can pass more, but "lost in the middle" and cost still argue for retrieval + reranking rather than dumping everything. Index **per-section** with good metadata so filtering can scope to relevant parts of huge documents. Principle: decompose large documents into retrievable, contextual units, and choose map-reduce/agentic strategies for genuinely document-wide questions.

**Q45.** What is semantic caching for RAG?

Semantic caching stores previous query-answer (and/or query-retrieval) pairs and serves a cached response when a **new query is semantically similar** to a cached one — not just exact-match. You embed the incoming query and check whether its similarity to any cached query exceeds a threshold; if so, return the cached answer (or cached retrieved chunks), skipping retrieval and generation. Benefits: large **latency** reduction and **cost** savings for repetitive/FAQ-style traffic, common in enterprise assistants. Risks: serving a **stale or subtly-wrong** cached answer when the new query differs in an important way the embedding missed, or when underlying data changed — so set a conservative similarity threshold, **invalidate** the cache on data updates, and exclude personalized/security-sensitive answers (a cached answer for one user must not serve another with different permissions). You can cache at the answer level (most savings, most risk) or the retrieval level (safer, regenerate the answer). Used carefully, semantic caching is a strong cost/latency optimization for high-volume RAG. Azure API Management supports it as a GenAI-gateway feature.

**Q46.** How do you decide between Azure AI Search and a dedicated vector DB?

**Azure AI Search** is the default for Microsoft-stack RAG: vector + keyword + **hybrid** search, the **semantic ranker**, **integrated vectorization**, indexers/connectors, security trimming, filtering, scoring profiles, and tight Azure integration (identity, networking, On Your Data, Foundry) — a complete managed retrieval platform, not just a vector store. Dedicated vector DBs (open-source or specialized) may offer specific features, cost profiles, or deployment models, and make sense if you're not Azure-centric, need a particular capability, or want to self-host. But for an Azure enterprise, AI Search usually wins on **integration, hybrid+semantic relevance, security, and operational simplicity** — you get reranking and integrated embedding without bolting together components. Choose a dedicated vector DB only with a strong reason (existing investment, multi-cloud, specific feature, extreme scale/cost optimization). For Microsoft roles, defaulting to **Azure AI Search with hybrid + semantic ranking + integrated vectorization** is the expected, well-justified answer, with awareness of when alternatives apply.

**Q47.** How do you measure and reduce retrieval-induced hallucination in production?

In production you can't rely only on offline eval. Instrument the pipeline to log, per request: the query, retrieved chunks (with scores), the final context, the answer, and citations. Run an online **groundedness/faithfulness check** (Azure groundedness detection or LLM-as-judge) on a sample (or all) of answers to estimate the hallucination rate, and **alert** when it rises. Capture **user feedback** (thumbs down, corrections) and flag low-confidence cases (low top retrieval scores) for review. To reduce hallucination: improve **recall** (hybrid + semantic ranking, better chunking) so correct evidence is present; enforce **strict grounding/refusal** prompts and confidence thresholds; **verify citations** before returning; and reduce noisy context via reranking. Establish a **feedback loop**: failures reveal missing/poor content to add or re-chunk, queries needing rewriting, or thresholds to tune. Track groundedness as a first-class production SLO alongside latency and cost. Continuous groundedness measurement + retrieval improvement + refusal logic keeps hallucination bounded over time.

**Q48.** What role do scoring/thresholds play in answer confidence?

Retrieval scores (BM25 scores, vector similarities, and especially the **semantic reranker score**) are proxies for how relevant the retrieved evidence is, and thus for answer confidence. By setting a **threshold** on the top reranker score, you decide whether to answer: above threshold, proceed; below, respond "I don't have that information" rather than forcing a low-evidence (hallucination-prone) answer. On Azure OpenAI On Your Data, a **strictness** parameter (1–5) effectively controls this — higher strictness requires stronger grounding and yields more "I don't know" responses, trading recall for precision/safety. Calibrate thresholds against your eval data: too strict and you refuse answerable questions; too loose and you hallucinate. Scores can also drive **routing** — low confidence triggers query rewriting, broader retrieval, multi-hop, or human escalation. Combine thresholds with citation requirements and groundedness checks. The key idea for interviews: retrieval scores aren't just for ranking — they're a confidence signal you can act on to decide when to answer, refine, or refuse.

**Q49.** How would you architect an enterprise RAG solution on Azure end-to-end?

**Ingestion/Indexing**: source connectors (SharePoint/Blob/ADLS/DB) → **Azure AI Search indexers** with a **skillset** using **Document Intelligence** for layout-aware extraction, **Split** skill for chunking, and **AzureOpenAIEmbedding** skill (text-embedding-3-large) for **integrated vectorization**; store vectors + text + metadata + ACLs in the index with **HNSW** and a **semantic configuration**; incremental/change-tracked indexing for freshness. **Query**: app (or **Azure OpenAI On Your Data**, or a custom **Microsoft Agent Framework** agent) does query rewriting → **hybrid + semantic-ranked** retrieval with **security trimming** by the caller's **Entra ID** → grounded prompt with citations → **Azure OpenAI** (gpt-4o) generation, streamed. **Cross-cutting**: **managed identity + RBAC** (Cognitive Services OpenAI User), **Private Endpoints/VNet**, **Key Vault**, **APIM** GenAI gateway for throttling/keys/quotas, **content filters/Content Safety**, **OpenTelemetry → App Insights** monitoring, **Azure AI Foundry evaluation** in CI, caching/prompt caching for cost, and PTUs for predictable load. This hits relevance (hybrid+semantic), security (trimming+identity+networking), quality (eval+groundedness), and operability (monitoring+cost controls) — the complete enterprise picture.

**Q50.** What are the top RAG anti-patterns to avoid?

(1) **Vector-only retrieval** — missing exact terms/identifiers; use hybrid + semantic ranking. (2) **No reranking** — passing first-stage results raw, so the best evidence may be buried. (3) **Over-stuffing context** — dumping many chunks, causing "lost in the middle," noise, and cost; rerank and pass few. (4) **Bad chunking** — fixed splits that sever tables/sections; use structure-aware chunking and overlap. (5) **No security trimming** — leaking documents users shouldn't see. (6) **No grounding/refusal prompt** — the model hallucinates instead of saying "I don't know." (7) **No citations/verification** — unverifiable, untrustworthy answers. (8) **Ignoring freshness** — stale or orphaned chunks after source updates/deletes. (9) **No evaluation harness** — tuning by vibes, unable to catch regressions. (10) **Ignoring prompt injection** from retrieved content. (11) **Reaching for fine-tuning** to add facts instead of RAG. (12) **No multi-turn query rewriting** in chat. (13) **Mismatched embedding model/metric** between index and query. Avoiding these — hybrid+rerank+tight context+trimming+grounding+citations+eval — is the difference between a demo and a dependable system.
