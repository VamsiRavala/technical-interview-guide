### Section 1.1 — .NET Core / .NET 5+ Fundamentals

**Q1. What's the difference between .NET Framework and .NET (Core)?**

**A.** They're two different runtimes:

| Aspect | .NET Framework vs .NET (Core / 5+) |
| ------------------- | ---------------------------------------------------------------------------------------- |
| **Origin** | Framework: 2002, Windows-only. Core: 2016, cross-platform. |
| **Cross-platform** | Framework: Windows only. Core: Windows, Linux, macOS. |
| **Performance** | Framework: slower. Core: significantly faster (5-10x for many workloads). |
| **Open source** | Framework: closed. Core: fully open source (.NET Foundation). |
| **Future** | Framework: maintenance only (4.8 is the last). Core: active development. .NET 9 current. |
| **Deployment** | Framework: machine-wide install. Core: self-contained or framework-dependent. |
| **Modern features** | Framework: limited. Core: latest C#, minimal APIs, AOT compilation, native integration. |

> In 2026, .NET 9 is current. Microsoft drops the 'Core' from the name starting .NET 5. New projects always start on modern .NET.

**Q2. Walk me through the .NET 9 application startup.**

**A.** Modern .NET uses the minimal API style:

```csharp
var builder = WebApplication.CreateBuilder(args);

// 1. Configure services (DI container)
builder.Services.AddControllers();
builder.Services.AddDbContext<AppDbContext>(opts =>
    opts.UseSqlServer(...));
builder.Services.AddScoped<IOrderService, OrderService>();

// 2. Configure logging, telemetry, auth
builder.Services.AddApplicationInsightsTelemetry();
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(opts => { opts.Authority = ...; opts.Audience = ...; });

var app = builder.Build();

// 3. Configure HTTP pipeline (middleware)
if (!app.Environment.IsDevelopment()) {
    app.UseExceptionHandler("/error");
    app.UseHsts();
}

app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();
```

> Key concepts: builder.Services configures the DI container. app.Use* configures the HTTP middleware pipeline (order matters!).

**Q3. Explain Dependency Injection (DI) in .NET.**

**A.** DI is the principle of providing dependencies from outside instead of creating them inside a class. .NET has built-in DI container (Microsoft.Extensions.DependencyInjection).

Three lifetimes:

| Lifetime | When to use |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Singleton** | One instance for the entire app lifetime. Use for: configuration, caches, stateless services. Beware: thread-safety required. |
| **Scoped** | One instance per HTTP request. Use for: DbContext, services that hold per-request state. Most common for business services. |
| **Transient** | New instance every time it's requested. Use for: lightweight stateless services. Not for: anything expensive to create. |

```csharp
// Registration
services.AddSingleton<IConfiguration>(config);
services.AddScoped<IOrderService, OrderService>();
services.AddTransient<IEmailSender, EmailSender>();

// Consumption (constructor injection)
public class OrderController(IOrderService orders, ILogger<OrderController> logger)
{
    [HttpPost]
    public async Task<IActionResult> Create(OrderDto dto) { ... }
}
```

**Q4. What's the difference between IEnumerable, IQueryable, and List?**

**A.** Three different abstractions for collections:

| Type | What it is / when to use |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **IEnumerable\<T>** | In-memory iteration. LINQ to Objects. Already-loaded data. Pull-based — items materialized as you iterate. |
| **IQueryable\<T>** | Query expression that hasn't executed yet. LINQ to SQL/EF Core. Filters and projections push down to the database. |
| **List\<T>** | Concrete in-memory collection. Materialized. Allows random access by index, .Count without iteration, .Add. |
| **IReadOnlyList\<T>** | Read-only view of an indexed collection. Use as return type when callers shouldn't mutate. |

```csharp
// Critical distinction with EF Core:

// IQueryable - filters at the database
var orders = _db.Orders.Where(o => o.Status == "pending");
// SQL: SELECT ... WHERE Status = 'pending'

// IEnumerable - filters in memory after loading EVERYTHING
var orders = _db.Orders.AsEnumerable().Where(o => o.Status == "pending");
// SQL: SELECT * FROM Orders (loads everything, filters in C#)
```

**Tip:** This is the #1 EF Core performance mistake. AsEnumerable() too early forces the entire table into memory. Always keep IQueryable as long as possible.

**Q5. What's async/await and why does it matter?**

**A.** async/await is .NET's syntax for asynchronous programming. It enables non-blocking I/O without callback hell.

How it works conceptually:

- 'await someTask' suspends the current method without blocking the thread.
- The thread is returned to the thread pool to handle other work.
- When the awaited task completes, execution resumes (possibly on a different thread).

Why it matters for performance:

- Web servers can handle far more concurrent requests with the same threads.
- DB calls, HTTP calls, file I/O — all should be async.
- Without async, threads block waiting for I/O, exhausting the thread pool under load.

```csharp
// Bad: blocks the thread
var data = httpClient.GetStringAsync(url).Result; // .Result blocks

// Good: thread is freed during the I/O wait
var data = await httpClient.GetStringAsync(url);
```

**Q6. What's a common async pitfall?**

**A.** Mixing sync and async (sync-over-async or async-over-sync). Both can deadlock or starve the thread pool.

```csharp
// Examples:

// PITFALL 1: .Result or .Wait() in ASP.NET — can deadlock
var data = SomeAsyncMethod().Result; // BAD
// FIX: async all the way down
var data = await SomeAsyncMethod();

// PITFALL 2: not awaiting fire-and-forget tasks
_ = SomeAsyncMethod(); // exception is swallowed silently
// FIX: await it, or use Task.Run with try/catch logging

// PITFALL 3: ConfigureAwait(false) in libraries
// Use in libraries to avoid capturing sync context
await SomeMethod().ConfigureAwait(false);
```

**Q7. What's the difference between Task and Task\<T>?**

**A.** Task represents an async operation that returns no value. Task\<T> represents one that returns a value of type T.

```csharp
// Common pattern:

// Task: void async method
public async Task SaveAsync(Order order)
{
    await _db.SaveChangesAsync();
}

// Task<T>: returns a value
public async Task<Order> GetAsync(Guid id)
{
    return await _db.Orders.FindAsync(id);
}

// ValueTask<T>: avoids allocation when sync path is common
public ValueTask<Order> GetCachedAsync(Guid id)
{
    if (_cache.TryGetValue(id, out var order))
        return new ValueTask<Order>(order); // sync path, no allocation
    return new ValueTask<Order>(_db.Orders.FindAsync(id).AsTask());
}
```

**Q8. What's a CancellationToken and when should I use one?**

**A.** CancellationToken lets long-running operations be cancelled cooperatively. ASP.NET Core provides one per HTTP request that fires when the client disconnects.

```csharp
// Always accept and propagate CancellationToken in async methods
public async Task<List<Order>> SearchAsync(
    string query,
    CancellationToken ct)
{
    return await _db.Orders
        .Where(o => o.Description.Contains(query))
        .ToListAsync(ct); // EF Core respects the token
}

// In controller, ASP.NET injects the request's token
[HttpGet]
public async Task<IActionResult> Search(
    string q,
    CancellationToken ct)
{
    var results = await _service.SearchAsync(q, ct);
    return Ok(results);
}
```

> Why it matters: if the user closes the browser, your DB query continues consuming resources without the token. With it, the query is cancelled — saves CPU, DB load, latency for other users.

### Section 1.2 — Entity Framework Core

**Q9. What's Entity Framework Core?**

**A.** Microsoft's ORM (Object-Relational Mapper) for .NET. Lets you work with databases as C# objects instead of writing SQL by hand.

Key concepts:

> **DbContext:** Represents a session with the database. Tracks changes to entities, persists them on SaveChangesAsync.
>
> **DbSet\<T>:** Represents a table. Query with LINQ.
>
> **Migrations:** Schema versioning. Generate from model changes, apply to database.
>
> **Change Tracking:** EF tracks which entities are added, modified, or deleted automatically.

**Q10. What's the difference between EF Core 'Lazy Loading' vs 'Eager Loading' vs 'Explicit Loading'?**

**A.** Three ways to load related entities:

| Approach | How it works |
| -------------------- | ------------------------------------------------------------------------------------------ |
| **Lazy Loading** | Related entities loaded automatically when accessed. Requires proxies. RISK: N+1 queries. |
| **Eager Loading** | Use .Include() to load related entities in the same query. Most explicit, most performant. |
| **Explicit Loading** | Manually load with await context.Entry(entity).Reference(...).LoadAsync(). |

```csharp
// Eager loading - 1 query with JOIN
var orders = await _db.Orders
    .Include(o => o.Customer)
    .Include(o => o.Lines)
        .ThenInclude(l => l.Product)
    .ToListAsync();

// Lazy loading (avoid in production) - N+1 queries
var orders = await _db.Orders.ToListAsync();
foreach (var o in orders)
{
    var customerName = o.Customer.Name; // Triggers a separate query for each order!
}
```

**Q11. What's the N+1 query problem?**

**A.** You execute one query to get a list, then for each item in the list you execute another query for its related data. 1 + N queries instead of 1 query with JOIN.

```csharp
// Example:

// 1 query: SELECT * FROM Orders
var orders = await _db.Orders.ToListAsync();

// N queries: 1 per order
foreach (var o in orders)
{
    var lines = await _db.OrderLines
        .Where(l => l.OrderId == o.Id).ToListAsync(); // SELECT for each!
}
```

Fixes:

- .Include() to JOIN in single query.
- Project to DTO with Select() — only loads what you need.
- Use AsSplitQuery() if Include creates a Cartesian explosion.

**Q12. What's the difference between Tracking and No-Tracking queries?**

**A.** By default, EF Core tracks every entity returned by a query so it can detect changes.

Tracking:

- EF tracks entities. SaveChanges persists modifications.
- Memory overhead — tracking metadata for each entity.
- Required if you'll modify and save.

No-Tracking:

- EF doesn't track. Just returns objects.
- Faster, less memory.
- Use for read-only queries (GET endpoints, reports).

```csharp
// Read-only - no tracking
var orders = await _db.Orders.AsNoTracking().ToListAsync();

// Need to modify - tracking required (default)
var order = await _db.Orders.FindAsync(id);
order.Status = "shipped";
await _db.SaveChangesAsync();
```

**Q13. What's a transaction in EF Core?**

**A.** EF Core wraps SaveChangesAsync in an implicit transaction by default — all changes succeed or none.

```csharp
// For explicit transactions across multiple SaveChanges:
using var tx = await _db.Database.BeginTransactionAsync();
try
{
    _db.Orders.Add(order);
    await _db.SaveChangesAsync();
    _db.AuditLog.Add(new AuditEntry("Order created", order.Id));
    await _db.SaveChangesAsync();
    await tx.CommitAsync();
}
catch
{
    await tx.RollbackAsync();
    throw;
}
```

**Q14. How do you handle EF Core migrations in production?**

**A.** Two approaches:

> **Apply at app startup (simple, risky):** _db.Database.MigrateAsync() at startup. Easy. But if multiple instances start at once, race conditions.
>
> **Separate deployment step (production-grade):** Generate SQL script (dotnet ef migrations script) and apply via DBA process or CI/CD. Decouples schema changes from app deployment.

Production rules:

- Backward-compatible migrations: never break running app version with new schema.
- Add columns nullable first; deploy code that writes; backfill; make NOT NULL in next deploy.
- Never DROP columns in same deploy as code that stops using them. Two-phase: stop using, then drop later.

### Section 1.3 — Performance & Memory

**Q15. What's the difference between value types and reference types?**

**A.** Value types (struct, int, bool, DateTime, custom struct): stored on the stack (or inline in the containing type). Copied by value when assigned. Fast, no GC pressure.

Reference types (class, string, arrays, interfaces): stored on the heap. Variables hold a reference. Garbage-collected.

Performance implications:

- Value types: cheap to allocate, cheap to copy if small. Become expensive if large.
- Reference types: allocation costs (GC). Pass by reference is cheap.
- Boxing: converting value type to object causes heap allocation. Avoid in hot paths.

**Q16. What's garbage collection in .NET and how does it work?**

**A.** Automatic memory management. The GC reclaims memory used by objects no longer referenced.

Generational GC:

> **Gen 0:** New objects. Collected frequently, cheaply. Most objects die young.
>
> **Gen 1:** Survived Gen 0 collection. Less frequent collection.
>
> **Gen 2:** Long-lived objects (caches, statics). Most expensive collection.
>
> **Large Object Heap (LOH):** Objects over 85KB. Collected only with Gen 2.

Performance implications:

- Allocations are cheap; collections are expensive. Reduce allocations in hot paths.
- Long-lived objects in Gen 2 are expensive to collect — keep caches reasonable.
- LOH allocations cause Gen 2 collections — avoid frequent large allocations.

**Q17. How do I profile a slow .NET application?**

**A.** Tooling progression from simple to deep:

- dotnet-counters: real-time metrics (CPU, GC, threads, exceptions). Free, built-in.
- dotnet-trace: collect ETW/EventPipe traces. Open in PerfView or Visual Studio.
- dotnet-dump: capture a process dump for offline analysis.
- Application Insights Profiler: production-safe sampling profiler.
- BenchmarkDotNet: micro-benchmarks for specific code paths in dev.
- Visual Studio Diagnostic Tools: integrated with debugger.

> First diagnose: is it CPU, memory, I/O, or contention? Then drill into the right tool.

**Q18. What's a memory leak in managed code? It's supposed to be impossible, right?**

**A.** 'Memory leak' in .NET means: you're holding references to objects you no longer need, so GC can't reclaim them.

Common causes:

- Static collections that grow without bound (caches without expiration).
- Event handlers not unsubscribed — the publisher holds a reference to the subscriber.
- Captured variables in lambdas extending object lifetimes.
- DbContext held too long (it tracks entities).
- Subscriptions to long-lived observables not disposed.

> Diagnosis: take memory snapshots at intervals; compare which types are growing.

**Q19. What's StringBuilder and when do I use it?**

**A.** Strings in .NET are immutable. Concatenating in a loop creates a new string each time, wasting memory.

```csharp
// BAD: creates N intermediate strings
string s = "";
for (int i = 0; i < 1000; i++)
    s += i.ToString();

// GOOD: single mutable buffer
var sb = new StringBuilder();
for (int i = 0; i < 1000; i++)
    sb.Append(i);
string s = sb.ToString();
```

> Use StringBuilder when: 5+ string operations, or any string building in a loop. For 2-3 simple concatenations, the regular + is fine and clearer.

**Q20. What's the difference between IEnumerable\<T> and Span\<T>?**

**A.** Span\<T> (added in .NET Core) is a stack-allocated view over contiguous memory (array, string, native buffer). Zero-allocation slicing.

When to use:

- Parsing: slice strings without allocating substrings.
- High-performance scenarios: low GC pressure.
- Buffer manipulation: pool buffers and slice them.

```csharp
// Old way - allocates substring
string fullName = "John Smith";
string firstName = fullName.Substring(0, 4); // new allocation

// New way - no allocation
ReadOnlySpan<char> firstName = fullName.AsSpan(0, 4);
```

> Span limitations: stack-only, can't be a field of a class, can't be used in async methods (use Memory\<T> for those cases).

### Section 1.4 — API Design with ASP.NET Core

**Q21. What's the difference between Controllers and Minimal APIs?**

**A.** Two ways to define HTTP endpoints in ASP.NET Core:

| Style | Pros and cons |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **Controllers** | Full-featured: filters, model binding, action results, OpenAPI auto-generation. More boilerplate. Better for large APIs. |
| **Minimal APIs** | Less boilerplate. Faster startup. Best for: small services, microservices, or specific endpoints. .NET 6+ feature. |

```csharp
// Controllers
[ApiController]
[Route("api/[controller]")]
public class OrdersController : ControllerBase
{
    [HttpGet("{id:guid}")]
    public async Task<IActionResult> Get(Guid id)
    {
        var order = await _service.GetAsync(id);
        return order is null ? NotFound() : Ok(order);
    }
}

// Minimal API
app.MapGet("/orders/{id}", async (Guid id, IOrderService svc) =>
{
    var order = await svc.GetAsync(id);
    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

**Q22. How do you version a REST API?**

**A.** Three common strategies:

> **URL versioning:** /api/v1/orders, /api/v2/orders. Most explicit. Easy to reason about.
>
> **Header versioning:** Custom 'api-version' header. Cleaner URLs. Harder to test in browser.
>
> **Query string:** /api/orders?api-version=1.0. Compromise. Less common.

```csharp
// Use Microsoft.AspNetCore.Mvc.Versioning library:
services.AddApiVersioning(opts =>
{
    opts.DefaultApiVersion = new ApiVersion(1, 0);
    opts.AssumeDefaultVersionWhenUnspecified = true;
    opts.ReportApiVersions = true;
});

[ApiVersion("1.0")]
[Route("api/v{version:apiVersion}/[controller]")]
public class OrdersController : ControllerBase { ... }
```

**Q23. How do you handle errors in an ASP.NET Core API?**

**A.** Use ProblemDetails (RFC 7807) for consistent error responses:

```csharp
// Global exception handler
app.UseExceptionHandler(errApp =>
{
    errApp.Run(async ctx =>
    {
        var feature = ctx.Features.Get<IExceptionHandlerFeature>();
        var problem = new ProblemDetails
        {
            Status = StatusCodes.Status500InternalServerError,
            Title = "An error occurred",
            Detail = feature.Error.Message,
            Instance = ctx.Request.Path
        };
        ctx.Response.StatusCode = problem.Status.Value;
        await ctx.Response.WriteAsJsonAsync(problem);
    });
});

// In actions, return ProblemDetails for known errors
if (order is null)
    return Problem(
        statusCode: 404,
        title: "Order not found",
        detail: $"No order with id {id}");
```

**Q24. What's CORS and how do you configure it?**

```csharp
// In Program.cs
builder.Services.AddCors(opts =>

app.UseCors("AllowApp");

// CRITICAL: lock down origins. Never use AllowAnyOrigin in production.
```

## PART 2 — SQL & DATABASE Q&A

Staff developers must be deep in SQL. Performance, transactions, schema design — these come up in every interview.

### Section 2.1 — SQL Fundamentals

**Q26. What's the difference between INNER JOIN, LEFT JOIN, and CROSS JOIN?**

**A.** Three ways to combine tables:

| Join | Behavior |
| -------------------------- | ------------------------------------------------------------------------------- |
| **INNER JOIN** | Returns only rows where match exists in BOTH tables. Most common. |
| **LEFT JOIN (LEFT OUTER)** | All rows from left + matched from right. Unmatched right = NULL. |
| **RIGHT JOIN** | All rows from right + matched from left. Same as LEFT JOIN with tables swapped. |
| **FULL OUTER JOIN** | All rows from both tables. NULLs on either side. |
| **CROSS JOIN** | Cartesian product — every row from left × every row from right. Rarely useful. |

```sql
-- All orders with customer info; orders without customer (orphans) excluded
SELECT o.Id, o.Total, c.Name
FROM Orders o
INNER JOIN Customers c ON o.CustomerId = c.Id

-- All customers, even those with no orders (Order columns NULL)
SELECT c.Name, o.Id, o.Total
FROM Customers c
LEFT JOIN Orders o ON o.CustomerId = c.Id
```

**Q27. What's the difference between WHERE and HAVING?**

**A.** WHERE filters rows BEFORE aggregation. HAVING filters AFTER aggregation.

```sql
-- Find customers with >5 orders totaling >$1000 each
SELECT CustomerId, COUNT(*) AS OrderCount, SUM(Total) AS GrandTotal
FROM Orders
WHERE Total > 1000 -- per-row filter
GROUP BY CustomerId
HAVING COUNT(*) > 5 -- post-aggregation filter
```

**Q28. What's an index and how do indexes work?**

**A.** An index is a data structure (typically B-tree) that speeds up reads at the cost of writes and storage.

Without an index, a query on 'WHERE Email = ...' scans the entire table (table scan). With an index on Email, the database walks the B-tree directly to matching rows.

Trade-offs:

- Reads on indexed columns: orders of magnitude faster.
- Writes (INSERT, UPDATE, DELETE): slower, since indexes must be updated.
- Storage: indexes consume disk.

Index types:

> **Clustered index:** Data IS the index. One per table (typically the primary key).
>
> **Non-clustered index:** Separate structure pointing to rows. Many per table.
>
> **Composite index:** Covers multiple columns. Order matters.
>
> **Covering index:** Includes all columns needed by the query, no row lookups required.

**Q29. How do I know if I need an index?**

**A.** Look at execution plans. SQL Server: SET STATISTICS IO ON or graphical plan in SSMS / Azure Data Studio.

Signs you need an index:

- Table Scan or Clustered Index Scan instead of Seek for selective queries.
- High logical reads on a small result set.
- Slow query log shows the same WHERE pattern repeatedly.

Signs you have too many indexes:

- Slow INSERT/UPDATE performance.
- Indexes that are never used (sys.dm_db_index_usage_stats in SQL Server).

**Q30. What's a transaction and what are ACID properties?**

**A.** Transaction: a unit of work that either fully succeeds or fully rolls back.

ACID properties:

> **Atomicity:** All operations succeed or none do.
>
> **Consistency:** Database moves from one valid state to another. Constraints, foreign keys enforced.
>
> **Isolation:** Concurrent transactions don't interfere (configurable via isolation levels).
>
> **Durability:** Committed transactions survive crashes (transaction log on disk).

**Q31. What are the SQL isolation levels?**

**A.** Trade-off between consistency and concurrency:

| Isolation Level | What it prevents / cost |
| ---------------------------- | --------------------------------------------------------------------------------- |
| **Read Uncommitted** | Nothing. Allows dirty reads (read uncommitted data). Fastest. Rarely used. |
| **Read Committed (default)** | Prevents dirty reads. Allows non-repeatable reads (same query, different result). |
| **Repeatable Read** | Prevents dirty + non-repeatable reads. Allows phantoms (new rows appear). |
| **Serializable** | Prevents all anomalies. Slowest. Highest contention. |
| **Snapshot (RCSI)** | MVCC-based. Readers don't block writers. Best of both worlds in many cases. |

> In SQL Server, enable READ_COMMITTED_SNAPSHOT for better concurrency without sacrificing safety.

**Q32. What's a deadlock and how do you fix it?**

**A.** Two transactions hold locks the other needs, neither can proceed. SQL detects and rolls back one (the 'victim').

Common cause: two queries access tables in different orders.

Mitigations:

- Always access tables in the same order across all transactions.
- Keep transactions short — fewer locks, less time held.
- Use lower isolation level when safe (Read Committed Snapshot).
- Add indexes to make queries faster (less time holding locks).
- Application: catch deadlock errors (1205 in SQL Server) and retry the transaction.

**Q33. What's a foreign key and why use one?**

**A.** A constraint that ensures a column references a valid row in another table.

Why use:

- Referential integrity — prevents orphan records.
- Catches bugs at the database level, not just app level.
- Self-documenting schema — relationships are visible.

Why some teams skip:

- Performance: every insert/update checks the FK. Negligible for most apps.
- Microservices: each service owns its data, FKs across service-owned tables don't make sense.
- Sharding: FKs across shards aren't enforceable.

**Q34. What's a stored procedure and when do you use one?**

**A.** A pre-compiled SQL routine stored in the database, called by name.

Pros:

- Performance: compiled once, cached execution plan.
- Security: grant EXEC permission without granting table access.
- Encapsulation: complex logic in one place.

Cons:

- Logic split between code and DB — harder to version.
- Database-specific (T-SQL, PL/SQL different).
- Hard to unit test.

> Modern preference: keep logic in app code, use ORM for data access. Stored procs only for: complex performance-critical operations, data warehouse ETL, legacy maintenance.

**Q35. What's the difference between TRUNCATE, DELETE, and DROP?**

**A.** Three ways to remove data:

| Operation | What it does |
| ------------- | ------------------------------------------------------------------------------------------------------- |
| **DELETE** | Removes rows. Logs each row. Can be filtered with WHERE. Triggers fire. Rollback-able. |
| **TRUNCATE** | Removes ALL rows. Minimally logged. Faster than DELETE FROM. Resets identity. Some triggers don't fire. |
| **DROP** | Removes the table itself (or other object) entirely. Cannot rollback after commit. |

**Q36. How do you optimize a slow query?**

**A.** Step-by-step approach:

- Get the execution plan. SQL Server: SET STATISTICS IO ON or graphical plan.
- Look for: table scans on large tables, key lookups, missing indexes, expensive sorts.
- Check WHERE clause: is it sargable (index-friendly)? Functions on columns prevent index use.
- Check JOIN columns: are they indexed?
- Check SELECT *: only return columns you need. Reduces data transfer + may enable covering indexes.
- Add indexes if needed. Validate with the plan after.
- Consider: query rewrite, denormalization for hot paths, caching.

```sql
-- BAD: function on column prevents index use
WHERE YEAR(OrderDate) = 2026

-- GOOD: range search uses the index
WHERE OrderDate >= '2026-01-01' AND OrderDate < '2027-01-01'
```

**Q37. What's the difference between OLTP and OLAP?**

**A.** Two database workload types:

| Aspect | OLTP vs OLAP |
| -------------- | ------------------------------------------------------------------------------------------------- |
| **Purpose** | OLTP: transactional. OLAP: analytical. |
| **Operations** | OLTP: lots of small transactions (INSERT/UPDATE one row). OLAP: few large scans/aggregations. |
| **Schema** | OLTP: normalized (3NF). OLAP: denormalized (star/snowflake). |
| **Latency** | OLTP: milliseconds. OLAP: seconds to minutes. |
| **Examples** | OLTP: order entry, banking, inventory. OLAP: BI dashboards, monthly reports, executive analytics. |
| **Tools** | OLTP: Azure SQL, Postgres, Cosmos. OLAP: Synapse, Snowflake, BigQuery. |

> Common pattern: OLTP system feeds OLAP system via ETL/CDC. Don't run heavy analytics on your OLTP database — it'll slow user-facing queries.

## PART 3 — REACT Q&A (DEVELOPER PERSPECTIVE)

Tech leads need to know React well enough to review PRs and make technology choices. You don't need to be a React-only specialist — Keith's role isn't React-focused.

### Section 3.1 — React Fundamentals

**Q38. What's React in one sentence?**

**A.** A JavaScript library for building user interfaces using composable components and a virtual DOM that efficiently updates the real DOM when state changes.

**Q39. What's a component in React?**

**A.** A reusable, self-contained piece of UI. Modern React uses functional components with hooks (class components are legacy).

```text
// Functional component with hooks
function OrderList({ customerId }) {
  const [orders, setOrders] = useState([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch(`/api/orders?customerId=${customerId}`)
      .then(r => r.json())
      .then(data => {
        setOrders(data);
        setLoading(false);
      });
  }, [customerId]);

  if (loading) return <Spinner />;
  return (
    <ul>
      {orders.map(o => <li key={o.id}>{o.total}</li>)}
    </ul>
  );
}
```

**Q40. What are the most common React hooks?**

**A.** Six you'll use constantly:

| Hook | Purpose |
| --------------- | ----------------------------------------------------------------------------------------------- |
| **useState** | Local component state. |
| **useEffect** | Side effects (data fetching, subscriptions, manual DOM updates). |
| **useRef** | Mutable reference that persists across renders. Often for DOM access. |
| **useMemo** | Memoize expensive calculations. Recompute only when dependencies change. |
| **useCallback** | Memoize functions. Prevents recreating on every render (stabilizes deps for child memoization). |
| **useContext** | Access React Context — share data across component tree without prop drilling. |

**Q41. What's the difference between useState and useReducer?**

**A.** Both manage local component state.

> useState: simple. Best for primitive values (string, number, bool) or small objects with 1-2 fields.
>
> useReducer: complex state with multiple sub-values, or when next state depends on previous in non-trivial ways. Same pattern as Redux.

```text
// useReducer for complex state
function ordersReducer(state, action) {
  switch (action.type) {
    case 'load_start': return { ...state, loading: true };
    case 'load_success': return { ...state, loading: false, orders: action.orders };
    case 'load_error': return { ...state, loading: false, error: action.error };
  }
}

function OrderList() {
  const [state, dispatch] = useReducer(ordersReducer, {
    loading: false, orders: [], error: null
  });
}
```

**Q42. What's the most common React mistake with useEffect?**

**A.** Missing dependencies in the dependency array. Causes stale closures over state.

```text
// BAD: count is captured stale
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, []); // missing count - logs old value forever

// GOOD: re-run effect when count changes
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, [count]);
```

> Use the eslint-plugin-react-hooks rule 'exhaustive-deps' to catch these automatically.

**Q43. What's the difference between Context and Redux?**

**A.** Both share state across components.

> Context: built into React. Best for: app-wide read-mostly data (theme, current user, locale).
>
> Redux (now Redux Toolkit): external library. Best for: complex client state with many updates, time-travel debugging needs, large teams that benefit from strict patterns.
>
> In 2026: many React apps don't need Redux. TanStack Query handles server state; Context handles app state; useState handles local state. Reach for Redux only when genuinely complex client state management is needed.

**Q44. What's TanStack Query and why is it important?**

**A.** Library for managing SERVER STATE in React. Handles caching, refetching, loading/error states, optimistic updates. Replaces ad-hoc useEffect+fetch patterns.

```text
// With TanStack Query
function OrderList({ customerId }) {
  const { data, isLoading, error } = useQuery({
    queryKey: ['orders', customerId],
    queryFn: () => fetch(`/api/orders?customerId=${customerId}`).then(r => r.json())
  });

  if (isLoading) return <Spinner />;
  if (error) return <Error msg={error.message} />;
  return <ul>{data.map(o => <li key={o.id}>{o.total}</li>)}</ul>;
}
```

> Why architects love it: replaces dozens of lines of manual cache/loading code. Handles refetch on focus, refetch on reconnect, deduplicates concurrent requests, keeps stale data visible while refetching. The biggest React mistake in 2026 is putting server data in Redux instead of TanStack Query.

**Q45. How do you optimize React app performance?**

**A.** Common levers, ordered by ROI:

- Code splitting: route-based with React.lazy + Suspense. Don't ship admin code to logged-out users.
- Memoize expensive components with React.memo when they receive same props but parent re-renders frequently.
- useMemo for expensive calculations. useCallback for callbacks passed to memoized children.
- Virtualize large lists with react-window — render only visible items.
- Defer non-critical updates with useTransition (React 18).
- Profile with React DevTools Profiler. Don't optimize without measuring.

**Q46. What are React Server Components?**

**A.** Components that run on the server, not the browser. Output HTML directly. Don't ship JavaScript to the client for those components.

Benefits:

- Smaller JS bundles.
- Direct database / API access from components.
- Faster initial page load.

Limitations:

- Can't use useState, useEffect, or browser APIs.
- Need framework support (Next.js App Router).

> This is the new direction in React (2024+). Mix server components for static/data-heavy parts with client components ('use client' directive) for interactive parts.

**Q47. When do you choose CSR vs SSR vs SSG?**

**A.** Three rendering strategies:

| Strategy | When |
| ----------------------------------------- | ------------------------------------------------------------------ |
| **CSR (Client-Side Rendering)** | Internal apps, dashboards. SEO doesn't matter. Default React app. |
| **SSR (Server-Side Rendering)** | Public marketing pages, e-commerce. Need SEO and fast first paint. |
| **SSG (Static Site Generation)** | Content rarely changes. Marketing, docs, blog. |
| **ISR (Incremental Static Regeneration)** | Mostly static, occasional update. Next.js feature. |

**Q48. How do you handle authentication in a React app?**

**A.** Standard pattern with OAuth/OIDC and a backend API:

- User clicks login. Redirect to identity provider (Entra ID).
- After login, identity provider redirects back with auth code.
- React app exchanges code for access token.
- Store access token in memory (NOT localStorage — vulnerable to XSS).
- Refresh token in HttpOnly cookie.
- Send access token as 'Authorization: Bearer ...' header on API calls.

> Use library: MSAL.js for Entra (Microsoft's official). Don't roll your own OAuth — too easy to get wrong.

**Q49. How do you debug a slow React component?**

**A.** React DevTools Profiler. Steps:

- Open React DevTools Profiler tab.
- Click 'Record' and reproduce the slow interaction.
- Stop. Look at the flame chart.
- Identify components that took the most time and rendered unnecessarily.
- Common causes: re-render of parent triggers all children, expensive calculation in render, large lists not virtualized.

> Use the 'Why did this render?' feature to see what triggered each re-render.

**Q50. What's the difference between controlled and uncontrolled components?**

**A.** Controlled: form input value comes from state. Updates via onChange handler.

> Uncontrolled: form input manages its own value. Read via ref.

```text
// Controlled (most common)
const [name, setName] = useState('');
<input value={name} onChange={e => setName(e.target.value)} />

// Uncontrolled
const inputRef = useRef();
<input ref={inputRef} defaultValue="John" />
// Read: inputRef.current.value
```

> Use controlled for: forms with validation, conditional logic. Use uncontrolled for: simple file uploads, integration with non-React code.

## PART 4 — TECH LEAD QUESTIONS

This is the heart of the role. Keith will spend significant time here.

### Section 4.1 — What Tech Leads Do

**Q51. What's the difference between a Senior Engineer and a Staff Developer / Tech Lead?**

**A.** Senior Engineer: deeply technical, owns features end-to-end, mentors juniors informally.

Staff Developer / Tech Lead: also deeply technical, but additionally:

- Sets technical direction for a team.
- Owns quality of the team's output (PRs, designs, production).
- Mentors deliberately, not just reactively.
- Translates business requirements into technical work.
- Represents the team in cross-team discussions.
- Owns the hardest, riskiest parts of the system.
- Identifies and pays down technical debt.

**Say it like this:** *'Senior engineers ship features. Tech leads ship features AND make the team better. The team's velocity, quality, and confidence improves over time when a good tech lead is in place. That's the thing being measured.'*

**Q52. How do you balance hands-on coding with leadership responsibilities?**

**A.** Honest answer:

**Say it like this:** *'In my experience, you should still write code as a tech lead — but pick what you write strategically. Avoid taking the simple tickets that grow juniors. Take the architectural cores, the integration points, the things that need careful design. Roughly 50-60% coding, 40-50% leadership: design reviews, code reviews, mentoring, planning, stakeholder communication. If you're 90% coding, you're not leading. If you're 10% coding, you've lost touch with the codebase.'*

**Q53. How do you handle code reviews as a tech lead?**

**A.** Code review is one of the highest-leverage things you do. Approach:

- Be timely. PRs sitting > 24 hours kill team velocity.
- Review WHY before HOW. Is this the right approach? Then check syntax.
- Distinguish blocking comments from suggestions. Use prefixes: 'BLOCKER:', 'NIT:', 'QUESTION:'.
- Praise good code, not just criticism. Public praise builds team.
- Don't bikeshed. Save energy for issues that matter — design, security, performance.
- Pair on hard reviews. Sometimes a 30-min call is faster than 20 review comments.
- If it's a learning moment for the author, explain WHY, link to docs, don't just say 'do this.'

**Q54. What's your approach to mentoring junior engineers?**

**A.** Concrete and structured. Don't just 'be available.'

**Say it like this:** *'I mentor with structure. For new engineers, I have weekly 1:1s — not just status, but 'what's confusing this week.' I assign work that stretches them but doesn't break them — give them the spec, let them design, then review and discuss. I deliberately let them struggle a bit before stepping in — that's where learning happens. For ADRs (architecture decision records), I have them draft, then I review and ask Socratic questions instead of giving answers. The goal is making them think like architects, not just write the code I'd write.'*

**Q55. How do you handle a teammate who's not delivering?**

**A.** Caring + direct. Don't immediately escalate.

**Say it like this:** *'First, a 1:1 to understand. Often it's not what it looks like — they're stuck on a hard technical problem, blocked by an external team, dealing with personal stuff. Once I understand, I can help: pair on the technical part, escalate the blocker, or just listen. If after that they're still not delivering, I loop in their manager — not as a complaint, but as 'here's what I've observed, here's what I've tried, you should know.' I don't try to manage someone who isn't reporting to me — but I do raise visibility when patterns persist.'*

**Q56. How do you handle disagreement with another engineer on a technical decision?**

**A.** Use this framework:

**Say it like this:** *'My approach: assume good intent. Most disagreements are about hidden assumptions, not bad faith. I get both sides to write down what we're optimizing for — often we find the goals are actually different, and once aligned, the technical choice becomes obvious. When the disagreement is genuinely about taste or experience, I push for a small spike: build it both ways and compare. Code is more honest than opinions. As tech lead, my role is making sure the team can resolve disagreements well — not necessarily making the final call myself.'*

**Q57. How do you decide which technical debt to pay down?**

**A.** Not all tech debt is equal. Prioritize by:

- Impact on velocity: which debt slows down EVERY new feature in this area?
- Risk: which debt could cause an outage or security incident?
- Cost to fix: small wins ship; massive refactors get deferred.
- Strategic alignment: does the area being refactored matter for the business roadmap?

> Practical: maintain a 'tech debt register.' Score each item on impact and effort. Allocate ~20% of every sprint to debt. Aggressively kill the 'this would be nice but never blocks anything' items.

**Q58. How do you set technical direction for a team?**

**A.** Multiple touchpoints, not a one-time announcement:

- Architecture Decision Records (ADRs) for major decisions. Written, reviewed, archived.
- Coding standards: lightweight document. Linters enforce automatically.
- Design reviews for any non-trivial feature. 30-min sync, decisions captured.
- Tech roadmap: 6-12 month view of where the codebase is going.
- Pair on the hard parts. Show how decisions get made by example.
- Bring in alignment: what's the business asking for? What's the platform team's direction?

> Direction isn't dictation. The best tech leads set principles and then let the team apply them, intervening only when off-track.

**Q59. How do you handle a stakeholder asking for something unrealistic?**

**A.** Negotiate concrete trade-offs. Don't just say no.

**Say it like this:** *'My approach: never just 'no.' I walk through the options. 'You want X by Y date. To meet that, we'd need to either skip the security review (I won't do that), drop the dashboard feature (option), accept tech debt we'll pay back in Q2 (option), or extend by 2 weeks (option). Which option works for you?' Now they're choosing. They feel respected. I'm protected from impossible commitments. We agree explicitly. Saying flat-out no makes you the obstacle. Offering choices makes you the partner.'*

### Section 4.2 — Production Ownership

**Q60. Walk me through how you handle a production incident.**

**A.** Step-by-step, calm:

- ACKNOWLEDGE: in the channel, 'I'm on it.' Sets expectations.
- STOP THE BLEEDING: immediate workaround. Could be rollback, config change, circuit breaker, scale-up. Customer impact reduction is the top priority.
- COMMUNICATE: status updates every 15 minutes. Even if no progress: 'still investigating.'
- DIAGNOSE: only after stopping the bleed. App Insights, logs, traces.
- CONFIRM RESOLUTION: don't declare 'all clear' from one OK metric. Watch 15+ minutes.
- WRITE-UP: blameless RCA within 24-48 hours. What happened, why, what we'll do differently.
- PREVENT RECURRENCE: action items with owners and dates. Review at next retro.

**Say it like this:** *'My approach is two-phase. Immediate: stop the bleeding. That's about minutes. Could be a rollback, a config flip, a circuit breaker. Permanent: actual fix with proper analysis. That's about understanding. I treat them as separate decisions because the urgency is different. The workaround needs to ship in 5 minutes; the fix needs to be RIGHT, even if it ships in 5 days.'*

**Q61. How do you do RCA (Root Cause Analysis)?**

**A.** 5 Whys is the simplest method:

> Symptom: customer checkout returned 500 errors for 15 minutes.
>
> Why? Order service was timing out on database calls.
>
> Why? Database connection pool was exhausted.
>
> Why? Connections were being created per-request after refactor.
>
> Why? Refactor removed connection pool config and tests didn't catch it.
>
> Why? We don't have a connection-pool integration test.
>
> Root cause: missing test coverage for connection pool configuration.
>
> Fix: add the test. Add a load test step to CI that would catch this class of bug.
>
> Blameless RCA principle: the system failed, not a person. People made decisions with the information they had at the time. Find systemic fixes, not someone to blame.

**Q62. How do you decide what to alert on?**

**A.** Three rules:

- Alert on user impact, not internal metrics. 'Error rate > 1%' beats 'CPU > 80%.' Users don't care about CPU.
- Make alerts actionable. Every alert must have a runbook: 'when this fires, do these steps.' Alerts that fire and someone dismisses are noise.
- Less is more. Too many alerts = alert fatigue = ignored alerts. Aggressive thresholds. Aggregate where possible.

> Architect-level: SLO burn rate alerts. Page on fast-burn (consuming budget at 14x normal); ticket on slow-burn (3x). This focuses attention on real problems, not noise.

**Q63. What's your debugging approach for a hard production bug?**

**A.** Systematic, not random:

- Reproduce: can I make it happen on demand? If yes, the rest is mechanical. If no, this is the hard part.
- Reduce: smallest possible scenario that exhibits the bug. Strip away noise.
- Hypothesize: what could cause this? List 3-5 possibilities.
- Test each hypothesis: instrument, add logging, run in isolation.
- Don't assume: verify each step. 'It can't be X' is the most dangerous phrase in debugging.
- Take notes: what you tried, what you ruled out. You'll forget by tomorrow.

> If stuck after 2 hours: pair with someone. Fresh eyes catch what tunnel vision misses.

**Q64. How do you handle on-call?**

**A.** On-call is a tax. Reduce it through engineering:

- Reduce alert volume: kill noisy alerts, fix root causes.
- Improve runbooks: every alert has clear steps. Runbook updates are a deliverable.
- Auto-remediation: bot fixes common issues without paging humans.
- Hand-off discipline: end-of-week summary, what's likely to fire.
- Post-incident: every page leads to an action item. Either prevent it or eliminate the alert.

> Goal: a quiet on-call rotation. If your team is paged constantly, that's an engineering failure to fix, not a culture to accept.

### Section 4.3 — Quality and Testing

**Q65. What's your testing strategy for a typical app?**

**A.** Test pyramid: lots of fast unit tests, some integration tests, few end-to-end tests.

| Test type | Purpose |
| --------------------- | ----------------------------------------------------------------------------------------------------------- |
| **Unit tests** | Test single class/method in isolation. Mock dependencies. Run in milliseconds. Hundreds-thousands of these. |
| **Integration tests** | Test multiple components together (e.g., API + database). Slower. Dozens-hundreds. |
| **End-to-end tests** | Test the full system from UI to DB. Slowest, most fragile. A few critical paths only. |
| **Performance tests** | Load tests, stress tests. Run periodically (nightly or pre-release). |
| **Security tests** | Static analysis, dependency scanning, DAST. Automated in CI. |

> Anti-pattern: ice-cream cone (lots of E2E, few unit). Slow, fragile, hard to maintain.

**Q66. How do you write a good unit test?**

**A.** FIRST principles:

> **Fast:** Milliseconds, not seconds. Slow tests don't get run.
>
> **Independent:** No shared state between tests. Order shouldn't matter.
>
> **Repeatable:** Same result every time. No flakiness.
>
> **Self-validating:** Test passes or fails clearly. No manual interpretation.
>
> **Timely:** Written close to the code it tests, ideally before.

```csharp
// Pattern (Arrange-Act-Assert):
[Fact]
public async Task PlaceOrder_WithValidData_ReturnsConfirmation()
{
    // Arrange
    var order = new Order { Id = Guid.NewGuid(), CustomerId = 1, Total = 100m };
    var mockRepo = new Mock<IOrderRepository>();
    mockRepo.Setup(r => r.SaveAsync(order)).ReturnsAsync(order);
    var service = new OrderService(mockRepo.Object);

    // Act
    var result = await service.PlaceOrderAsync(order);

    // Assert
    Assert.Equal(OrderStatus.Confirmed, result.Status);
    mockRepo.Verify(r => r.SaveAsync(order), Times.Once);
}
```

**Q67. What's the difference between Mock, Stub, Fake, and Spy?**

**A.** Different types of test doubles:

| Type | What it does |
| -------- | ------------------------------------------------------------------------ |
| **Stub** | Returns canned responses. No verification. |
| **Mock** | Records calls. Verifies expectations afterward. |
| **Fake** | Working implementation but simplified (in-memory DB instead of real DB). |
| **Spy** | Wraps real object, records calls but lets actual execution happen. |

> In .NET: Moq library covers most cases (mocks + stubs). NSubstitute is a popular alternative.

**Q68. When do you write tests vs when do you skip?**

**A.** Pragmatic, not dogmatic:

> **Always test:** Business logic, edge cases, anything that's failed before, anything safety/security/money-critical.

**Q70. How do you make sure code reviews catch bugs?**

**Q82. How do you publish to Service Bus from .NET?**

**Q88. How does cost work for Cosmos DB?**

**A.** Three pricing modes:

### During the Interview — 5 Rules

- Slow down. Pauses are fine. Architects think before speaking.
- Lead with trade-offs, not features. 'We picked X because Y had cost Z.'
- Quantify. Numbers beat adjectives. 'p99 dropped from 2s to 200ms.'
- Use 'I' for your contributions; 'we' for team wins.
- If stuck, say 'Let me think for ten seconds' — then take them.

### If You Don't Know Something

**Say it like this:** *'I haven't worked with [X] directly. My understanding is [one-sentence positioning]. The closest thing I've shipped is [Y]. The pattern transfers because [reason]. I'd want to do a small spike before claiming production knowledge.'*

### Things to NEVER Say

- 'Best practice' — without specifying for what context.
- 'Industry standard' — vague, defensive.
- 'Cutting-edge,' 'world-class,' 'enterprise-grade' — empty marketing words.
- 'I think we...' — uncertain about your own work.
- 'They wouldn't let me...' — passive, blames others.
- Faking knowledge of something you haven't done.
