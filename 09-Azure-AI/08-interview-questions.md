## Azure OpenAI Service (Top 50)

**Q1.** What is Azure OpenAI Service and how does it differ from OpenAI's API?

Azure OpenAI Service provides OpenAI's models (GPT-4o, GPT-4.1, o-series reasoning models, embeddings, DALL·E, etc.) through Azure's enterprise platform with the same model capabilities but Azure's governance, security, and compliance. Key differences from OpenAI's public API: you access models via **deployments** in your Azure resource (and reference **deployment names**, not raw model names); authentication can use **Microsoft Entra ID / managed identity + RBAC** instead of just API keys; data handling meets Azure enterprise commitments—your prompts/completions are **not used to train** the foundation models and stay within your Azure tenant/region (data residency); you get **Private Endpoints/VNet** integration, **Azure Monitor** observability, **content filters** via Azure AI Content Safety, **SLAs**, regional availability, and integration with the broader Azure AI Foundry ecosystem (On Your Data, agents, evaluation). It also offers Azure-specific deployment/billing options like **Provisioned Throughput Units (PTUs)**. In short: same models, plus enterprise identity, networking, compliance, monitoring, and the Azure ecosystem—which is exactly why Microsoft-centric enterprises choose it.

**Q2.** What is a deployment and a deployment name?

In Azure OpenAI you don't call a model directly; you create a **deployment**—a named instance of a specific model and version within your resource, with an associated deployment type (Standard/PAYG, Provisioned/PTU, Global, etc.) and capacity/quota. Your application then targets the **deployment name** (a string you choose, e.g., `gpt-4o-prod`) in API calls, not the underlying model name. This indirection is powerful: you can swap the underlying model/version behind a stable deployment name, run multiple deployments of the same model with different quotas or content-filter configs, and route traffic by deployment. It does mean SDK calls reference `deployment` (Azure) where the OpenAI SDK references `model`. Best practice: use stable, environment-specific deployment names (`chat-prod`, `chat-staging`), keep them in config not code, and decouple them from model versions so you can upgrade models without app changes. Understanding deployment-name indirection is fundamental to operating Azure OpenAI.

**Q3.** Explain PTU vs PAYG vs spillover.

**PAYG (Pay-As-You-Go / Standard)** bills per token consumed with shared capacity—great for variable/low-to-moderate, bursty workloads; you only pay for what you use, but you share capacity and are subject to quota and potential 429s under contention. **PTU (Provisioned Throughput Units)** reserve dedicated model capacity for a fixed price (hourly, or discounted with monthly/annual reservations), giving **predictable, consistent latency and guaranteed throughput**—ideal for steady, high-volume, latency-sensitive production. PTUs can be more cost-effective than PAYG above a certain sustained utilization. **Spillover** combines them: you run on PTUs for baseline capacity and **overflow** excess traffic to a PAYG (Standard) deployment when PTU capacity is exhausted, so bursts above your provisioned throughput still succeed (on PAYG pricing) instead of getting throttled. This hybrid gives predictable performance and cost for the base load plus elasticity for spikes. Choose PAYG for variable/dev workloads, PTU for steady production needing SLAs/latency, and PTU + spillover for production with burstiness.

**Q4.** What are quota, TPM, and RPM?

Azure OpenAI enforces capacity limits per deployment/region/subscription. **TPM (Tokens Per Minute)** is the primary quota unit for Standard deployments—the max tokens (prompt + completion) processable per minute; you allocate TPM to deployments from your subscription's regional quota. **RPM (Requests Per Minute)** is a derived/associated request-rate limit (Azure historically ties RPM to TPM, e.g., a fixed ratio like 6 RPM per 1K TPM). Exceeding either yields **HTTP 429 (Too Many Requests)**. Quota is assigned per region per model family, so you distribute it across deployments and can request increases via Azure support. For PTU deployments, capacity is governed by provisioned units (throughput) rather than TPM quota. Practical implications: size TPM for peak load, distribute quota across deployments/regions, implement retry/backoff on 429s, and monitor utilization. Understanding that **both** TPM and RPM can trigger throttling—and that quota is regional and per-model—is essential for capacity planning and avoiding production 429 storms.

**Q5.** How do you handle 429 errors and implement retries?

A **429** means you've hit TPM/RPM quota (or PTU capacity). Handle it with **exponential backoff with jitter**, and crucially **respect the `Retry-After` header** Azure returns, which tells you how long to wait. Don't retry instantly or you amplify the overload. The Azure OpenAI SDKs include built-in retry logic for 429/transient errors (configurable `max_retries`), but you should still design for it. Strategies: (1) backoff + jitter + honor `Retry-After`; (2) **distribute load** across multiple deployments/regions and load-balance (an **APIM GenAI gateway** can do smart routing and retry across backends); (3) right-size **TPM quota** and use **PTUs** (with **spillover** to PAYG) for predictable capacity; (4) **queue/throttle** client-side to stay under limits; (5) reduce token usage (shorter prompts, caching) to lower TPM pressure. For background/bulk work, use the **Batch API**. Monitor 429 rates as an SLO. The interview-grade answer: backoff with jitter honoring `Retry-After`, plus capacity strategy (PTU/quota/APIM) so 429s are rare in the first place.

```csharp
// Azure.AI.OpenAI SDK supports configurable retries via ClientOptions

```

**Q6.** What are content filters and configurable severity levels?

Azure OpenAI applies **content filtering** (powered by Azure AI Content Safety) to both **prompts (input)** and **completions (output)**, classifying content across categories—**hate, sexual, violence, self-harm**—plus additional features like **jailbreak/prompt-injection detection**, **protected material** (code/text), and **groundedness** detection. Each category is scored at a **severity** level (safe, low, medium, high), and you can configure thresholds via **custom content filter configurations** assigned to a deployment, choosing at which severity to block for input and output independently. Default blocks medium and high. Filtered content returns a **`content_filter` finish reason** and an error/annotation indicating which category triggered it. For approved scenarios you can apply for **modified filters** (e.g., relaxed thresholds) and **abuse-monitoring opt-out**. Best practices: tune severities to your use case, handle filtered responses gracefully in the app (don't crash), log filter events, and combine with your own guardrails. Knowing that filtering is **bidirectional**, **per-category with severity thresholds**, and **configurable per deployment** is the key point.

**Q7.** What is function calling in Azure OpenAI?

Function calling (now generalized as **tools**) lets the model invoke developer-defined functions to fetch data or take actions. You describe functions to the API as JSON schemas (name, description, parameters); when appropriate, the model returns a **tool call** with a function name and JSON arguments instead of a text answer. Your code executes the function and sends the result back; the model then produces a grounded final response. This bridges the LLM with real systems—databases, APIs, calculators—and is the foundation of agents and RAG-as-a-tool. Azure OpenAI supports **parallel tool calls** (multiple in one turn) and **tool_choice** to force/auto/none. Best practices: write clear function descriptions and typed parameter schemas (the model relies on them), validate arguments before executing (the model can produce bad/hallucinated args), keep functions idempotent where possible, and never blindly trust outputs—apply authorization in the function itself. Function calling pairs naturally with **structured outputs** for reliable argument formatting. It's the core mechanism behind tool-using agents on Azure OpenAI.

**Q8.** What are structured outputs and JSON mode?

Both make the model emit machine-parseable JSON instead of free text. **JSON mode** (`response_format = {"type": "json_object"}`) guarantees the output is **valid JSON** but not that it matches a specific schema. **Structured Outputs** (`response_format = {"type": "json_schema", ...}` with `strict: true`, supported on newer GPT-4o+ models) goes further: the output is **constrained to conform to a JSON Schema you supply**, so fields, types, and required properties are guaranteed—eliminating brittle parsing and re-asks. Many SDKs let you pass a Pydantic/C# class and auto-derive the schema. Use structured outputs for tool arguments, data extraction, and any case where downstream code consumes the result.

```json
{ "type": "json_schema",
  "json_schema": { "name": "invoice", "strict": true,
    "schema": { "type": "object",
      "properties": { "vendor": {"type":"string"}, "total": {"type":"number"} },
      "required": ["vendor","total"], "additionalProperties": false } } }
```

Prefer **Structured Outputs** over plain JSON mode when you need schema guarantees; it's more reliable for production integration.

**Q9.** How do embeddings work in Azure OpenAI?

Embeddings convert text into fixed-length numeric vectors capturing semantic meaning, so similar text yields nearby vectors—used for search/RAG, clustering, classification, and recommendations. On Azure you deploy an embedding model (**text-embedding-3-large**, **text-embedding-3-small**, or legacy **text-embedding-ada-002**) and call the embeddings endpoint with input text to get vectors. The `-3` models support **dimension reduction** via a `dimensions` parameter (e.g., reduce 3072→1024) to cut storage/latency with modest quality loss. Key points: use the **same model and dimensionality** for indexing documents and embedding queries; normalize/compare with **cosine similarity**; batch inputs for throughput (and use the **Batch API** for large indexing jobs at lower cost); and mind token limits per input (so chunks aren't truncated). Embeddings are central to RAG—paired with Azure AI Search's vector index (or integrated vectorization, which calls your embedding deployment automatically). For Azure RAG, text-embedding-3-large with cosine is the strong default; -small or dimension reduction when cost/latency matters.

**Q10.** Can you fine-tune models on Azure OpenAI, and when should you?

Yes—Azure OpenAI supports **fine-tuning** of supported models (e.g., GPT-4o-mini, GPT-4.1 family, and others as availability evolves) by uploading a **JSONL** dataset of prompt/completion (chat-format) examples; Azure trains a custom model you then **deploy** under your own deployment name. Methods include supervised fine-tuning and, for some models, **DPO** (preference) and distillation. When to use it: to teach **behavior, style, tone, format, or domain phrasing**, to improve reliability on a narrow task, or to **shorten prompts** by baking in instructions/few-shot examples (reducing per-call tokens/latency/cost at scale). When **not** to: to add **factual knowledge** (use RAG—fine-tuning doesn't reliably inject facts and they go stale). Considerations on Azure: training/hosting costs (fine-tuned deployments may bill for hosting time), data quality/quantity (hundreds–thousands of clean examples), region availability, evaluation against a baseline, and maintenance (retrain to update). Rule of thumb: **RAG for knowledge, fine-tuning for behavior**; start with prompting/few-shot, fine-tune only when there's a persistent need prompting can't meet.

**Q11.** How do you secure Azure OpenAI with networking and Private Endpoints?

To keep traffic off the public internet, deploy the Azure OpenAI resource with **Private Endpoints**: a private IP in your VNet maps to the resource, and you **disable public network access**, so only resources in (or peered to) the VNet—and on-prem via ExpressRoute/VPN—can reach it, resolving via **Private DNS zones**. This prevents data exfiltration and exposure. Combine with **VNet integration** for your compute (App Service/AKS/Functions) so calls stay on the Microsoft backbone. Layer additional controls: **NSGs/firewall**, an **APIM GenAI gateway** in front for centralized auth/throttling/logging, and **managed identity** (no keys traversing the network). For other connected services (Azure AI Search, Storage), give them Private Endpoints too so the whole RAG data flow is private. Use **diagnostic logging** to Log Analytics over private links. This network isolation is a standard enterprise/compliance requirement and frequently asked: the key elements are **Private Endpoint + disable public access + Private DNS + VNet-integrated callers + managed identity**, optionally fronted by APIM.

**Q12.** How does managed identity and RBAC work with Azure OpenAI?

Instead of API keys, use **Microsoft Entra ID** authentication: assign your app a **managed identity** (system- or user-assigned) and grant it an Azure RBAC role on the Azure OpenAI resource. The key data-plane role is **Cognitive Services OpenAI User** (call models / inference); **Cognitive Services OpenAI Contributor** additionally allows management like creating deployments. The app uses `DefaultAzureCredential` (or `ManagedIdentityCredential`) to acquire a short-lived AAD token for scope `https://cognitiveservices.azure.com/.default` and sends it as a Bearer token—no secret stored or rotated. Benefits: no key leakage, automatic rotation, centralized access control and auditing, and conditional-access/PIM support. Best practice: **disable local (key) auth** on the resource to enforce identity-only access, apply **least privilege** (User vs Contributor), use **user-assigned identities** for shared scenarios, and combine with Private Endpoints. `Azure.Identity` + `Azure.AI.OpenAI` with `DefaultAzureCredential` is the canonical secure pattern, and naming **Cognitive Services OpenAI User** signals real Azure fluency.

**Q13.** What data privacy and residency guarantees does Azure OpenAI provide?

Azure OpenAI runs within your Azure tenant and **selected region**, so prompts and completions are **processed in that region** (data residency), supporting compliance needs. Microsoft's commitments: your **prompts, completions, embeddings, and training data are NOT used to train or improve the OpenAI/Microsoft foundation models** and are not shared with OpenAI; data is yours, encrypted at rest and in transit. By default, prompts/completions may be **temporarily stored (up to 30 days) for abuse monitoring**, accessible only to authorized Microsoft reviewers and only on flagged activity—and eligible customers can **apply to opt out of abuse monitoring and human review** so no prompts/completions are stored. Fine-tuned models and uploaded data stay within your resource/region. Combine with **Private Endpoints**, **CMK (customer-managed keys)** for encryption, **managed identity**, and audit logging for a full posture. The headline points interviewers want: **regional data residency**, **your data isn't used to train the models**, **no data shared with OpenAI**, and an **abuse-monitoring opt-out** for sensitive workloads—all under Azure's compliance certifications.

**Q14.** How do you monitor Azure OpenAI?

Use **Azure Monitor** integration. Azure OpenAI emits **metrics** (token usage—processed prompt/generation tokens, request count, latency, 429/throttling counts, PTU utilization) to **Azure Monitor Metrics**, and **diagnostic logs** (requests, errors, content-filter events) to **Log Analytics / Application Insights** when you enable diagnostic settings. Build dashboards and **alerts** on: TPM/PTU utilization (capacity), 429 rate (throttling), latency p95/p99, error rates, and token spend (cost). For end-to-end app tracing, instrument with **OpenTelemetry** and send traces (prompt/response metadata, token counts, latency, finish reasons) to Application Insights, correlating across RAG/agent steps. If fronting with **APIM**, capture gateway-level analytics (per-consumer usage, throttling) and enforce/monitor quotas there. Azure AI Foundry also provides usage and evaluation views. Operational essentials: track **cost (tokens), capacity (TPM/PTU), reliability (429/errors/latency)**, and **safety (content-filter triggers)**, with alerting and per-application attribution.

**Q15.** What is the Batch API and when do you use it?

The Azure OpenAI **Batch API** processes large volumes of requests **asynchronously** at a **discounted price** (typically ~50% off Standard) with a target turnaround (e.g., within 24 hours), using separate batch quota that doesn't consume your real-time TPM. You upload a **JSONL** file of requests, submit a batch job, then poll/retrieve results when complete. Use it for **non-interactive, high-volume** workloads where latency doesn't matter: bulk **embedding generation** for indexing a large corpus, mass **classification/summarization/extraction**, dataset labeling, offline evaluations, or back-catalog processing. Benefits: lower cost and no contention with your interactive deployments' quota. Trade-offs: not for real-time use, and completion time isn't guaranteed instant. For building RAG, the Batch API is the cost-smart way to embed and process large document sets during initial indexing or periodic reprocessing. The key interview point: **Batch = async, cheaper, separate quota, for large non-latency-sensitive jobs**, complementing real-time Standard/PTU deployments for online traffic.

**Q16.** What model families and versions are available, and how do you manage versioning?

Azure OpenAI offers several families: **GPT-4o / GPT-4o-mini** (multimodal, fast), **GPT-4.1** family (strong general models with large context), **o-series reasoning models** (o1/o3/o4-mini—deeper reasoning for complex tasks, different pricing/latency), **embeddings** (text-embedding-3-large/-small, ada-002), plus image/audio models *(verify current GA status)*. Each model has dated **versions** (e.g., a specific snapshot) and an API version separate from the model version. Versioning management: choose **specific model versions** for production stability (so behavior doesn't change unexpectedly), and be aware of Azure's **auto-update** option that can move a deployment to newer versions—often you **pin** the version and upgrade deliberately after testing. Track **model retirement/deprecation** dates (Azure publishes them) and plan migrations. Keep the **API version** explicit in calls and update it intentionally. Use the **deployment-name indirection** to swap versions behind a stable name. The disciplined approach: pin versions, test new versions against an eval suite before upgrading, monitor deprecation timelines, and treat model upgrades as managed changes.

**Q17.** How do you do "On Your Data" with Azure OpenAI?

**On Your Data** lets the chat completions API perform RAG against your data (most commonly an **Azure AI Search** index) with minimal code: you attach a **data source** to the request, and the service retrieves relevant chunks, grounds the model's answer, and returns **citations**. You configure: the search **endpoint/index**, **authentication** (managed identity recommended), **query type** (recommend **vector** or **hybrid + semantic**), **fields mapping** (content, title, URL, vector, filter), **top-n** documents, **strictness** (how strongly grounded answers must be), and **in-scope** (restrict answers to retrieved data). It supports integrated vectorization and returns the documents used so you can render citations. Benefits: fast, managed grounding/citations without building the full pipeline; great for enterprise chatbots. Limits: less control over custom reranking, complex multi-hop, or bespoke prompting—where you'd build a custom RAG with AI Search + Azure OpenAI (or an agent). You can call it via the SDK or the Foundry playground (which generates code). It's the quickest path from "I have docs in AI Search" to "grounded chatbot with citations."

**Q18.** How do you optimize cost on Azure OpenAI?

Cost is driven by **tokens** (input + output) and deployment type. Levers: (1) **Right-size the model**—use **GPT-4o-mini** or smaller where quality allows; reserve premium/reasoning models for hard tasks. (2) **Reduce tokens**—concise prompts, trimmed RAG context (rerank, pass few chunks), cap `max_tokens`, and remove redundant few-shot via fine-tuning if persistent. (3) **Prompt caching**—Azure discounts repeated **cached input tokens** (large static system prompts/context), cutting cost and latency. (4) **Batch API** (~50% off) for bulk/offline work. (5) **PTUs (with reservations)** for steady high volume—often cheaper per token than PAYG above sustained utilization, with spillover for bursts. (6) **Caching answers** (semantic cache) for repeated queries. (7) **Dimension-reduced embeddings** to cut storage/search cost. (8) **Monitor token spend per feature** (Azure Monitor) and optimize the biggest consumers. (9) Avoid unnecessary calls (gate optional steps like query rewriting/multi-hop). The senior framing: measure token usage, match model/deployment type to workload pattern, exploit caching/batch, and treat tokens as the primary cost lever.

**Q19.** What is the APIM GenAI Gateway pattern?

Placing **Azure API Management (APIM)** in front of one or more Azure OpenAI deployments creates a **GenAI gateway**—a centralized control plane for LLM traffic. Capabilities (via APIM's GenAI policies): **token-based rate limiting/quotas** per consumer (enforce TPM fairly across teams/apps), **load balancing and failover** across multiple Azure OpenAI backends/regions (smart routing, retry on 429, circuit breaking), **caching** (including semantic caching), **centralized auth** (managed identity to backends, subscription keys/JWT to clients), **logging/analytics** of token usage and latency per consumer for chargeback/observability, and **request/response transformation and content-safety integration**. Benefits: you decouple clients from specific deployments, enforce governance and cost controls centrally, improve reliability (multi-backend failover mitigates 429s), and get per-consumer usage metering—crucial when many apps/teams share Azure OpenAI capacity. Microsoft publishes reference policies/labs for this pattern. For an enterprise architecture answer, the **APIM GenAI gateway** demonstrates how to operationalize Azure OpenAI at scale with **throttling, load balancing/failover, token metering, caching, and centralized security**.

**Q21.** How do you call Azure OpenAI from .NET securely?

Use the **`Azure.AI.OpenAI`** client with **`Azure.Identity`** managed identity—no API keys. The identity needs the **Cognitive Services OpenAI User** role; locally `DefaultAzureCredential` falls back to your dev identity.

```csharp
using Azure.AI.OpenAI;
using Azure.Identity;

var client = new AzureOpenAIClient(
    new Uri("https://my-aoai.openai.azure.com/"),
    new DefaultAzureCredential());

var chat = client.GetChatClient("gpt-4o"); // deployment name
var resp = await chat.CompleteChatAsync(
    [ new SystemChatMessage("You are concise."),
      new UserChatMessage("Summarize Azure OpenAI in one line.") ]);
Console.WriteLine(resp.Value.Content[0].Text);
```

Best practices: pass credentials via `DefaultAzureCredential` (managed identity in Azure), reference the **deployment name** (not model), keep endpoint/deployment in **configuration** (Key Vault / App Config), set a sensible **retry policy** (SDK honors 429/`Retry-After`), enable **OpenTelemetry**, and run behind **Private Endpoints/APIM**. This identity-first, config-driven .NET pattern is exactly what Microsoft-stack interviewers expect from a senior .NET/Azure engineer.

**Q22.** What is prompt caching and how does it save cost/latency?

Prompt caching reuses previously processed **input tokens** when the **prefix** of a prompt repeats across requests—common when you send the same large **system message**, instructions, or few-shot examples (and increasingly RAG context) on every call. Azure OpenAI automatically caches matching prompt prefixes (above a minimum token threshold) and bills **cached input tokens at a significant discount** (and processes them faster), reducing both **cost** and **time-to-first-token**. To benefit, keep the **static, repeated content at the start** of the prompt and the variable content (the user's specific question) at the end, so the cacheable prefix is stable. It's especially valuable for chat assistants and agents with long fixed system prompts and for RAG where instructions are constant. You can observe cached-token counts in usage. No code change is required beyond structuring prompts prefix-stable. The interview point: **put invariant content first**, and prompt caching transparently cuts cost/latency on repeated long prefixes—an easy, high-impact optimization for production LLM apps.

**Q23.** How do you choose between Standard, Global, and Data Zone deployment types?

Azure OpenAI deployment types trade off **data residency** vs **capacity/availability**. **Standard (regional)** processes requests **in the resource's region**—best for strict in-region data residency, but capacity is limited to that region. **Global Standard** routes requests to **available capacity across Microsoft's global infrastructure**, giving higher throughput/availability and often access to the newest models first, but **data may be processed outside your region** (though Microsoft still doesn't train on it)—use when residency permits. **Data Zone** is a middle ground: requests are processed within a **broader geographic zone** (e.g., a Data Zone covering multiple regions, like EU or US), balancing residency (data stays within the zone/geography) with better capacity than a single region. There are PAYG and Provisioned (PTU) variants of these. Choose: **Standard** for strict single-region residency; **Data Zone** to keep data in a compliance geography while gaining capacity; **Global** for maximum throughput/model availability when cross-region processing is acceptable. Matching deployment type to **residency requirements and capacity needs** is a key architecture decision.

**Q24.** How do you handle long context windows effectively?

Modern Azure OpenAI models offer large context windows (e.g., 128K+ tokens, some much larger), but bigger isn't automatically better. Pitfalls: **cost** (you pay per input token), **latency** (more tokens = slower), and **"lost in the middle"** (the model under-attends to mid-context content). Effective use: (1) **Retrieve and rerank** rather than dumping everything—pass only the most relevant chunks (RAG) even when you *could* fit more. (2) **Order** content so the most important material is near the start/end. (3) **Summarize/compress** older conversation turns instead of resending full history. (4) Exploit **prompt caching** by keeping static context at the prefix. (5) For genuinely large inputs, use **map-reduce** or **iterative** processing rather than one giant prompt. (6) Reserve enough budget for the **completion** (`max_tokens`). Reasoning (o-series) models also consume tokens for hidden reasoning—budget accordingly. The principle: treat context as a scarce, costly resource—use **precision (retrieval/reranking/summarization)** over volume, even with big windows, for better quality, latency, and cost.

**Q25.** What are reasoning (o-series) models and when to use them?

The **o-series** (o1, o3, o4-mini, etc.) are models trained to **reason step-by-step internally** before answering, spending extra "thinking" compute (hidden reasoning tokens) to tackle hard problems—complex math, multi-step logic, advanced coding, scientific/analytical tasks—often outperforming standard chat models on these *(verify current GA status)*. Trade-offs: **higher latency and cost** (you pay for reasoning tokens), so they're overkill for simple tasks. API differences: they use a **reasoning effort** parameter (low/medium/high), may not support all chat features (e.g., certain system-message/temperature behaviors differ), and you should budget tokens for the internal reasoning. When to use: route **only the genuinely hard, high-stakes reasoning tasks** to o-series; use **GPT-4o/4o-mini** for general chat, RAG answering, and simple tools where speed/cost matter. A common production pattern is **model routing**: a cheap model handles most traffic and escalates complex queries to a reasoning model. The interview point: o-series = deeper reasoning at higher cost/latency; use selectively and route by task difficulty rather than defaulting to them.

**Q26.** How do you implement multi-region failover for Azure OpenAI?

For high availability, deploy Azure OpenAI in **multiple regions** and route across them so a regional outage or capacity exhaustion doesn't take you down. Patterns: (1) **APIM GenAI gateway** as the front door doing **load balancing, retry, circuit breaking, and failover** across regional backends—on 429/5xx it routes to a healthy region; this also smooths capacity (more aggregate TPM). (2) **Traffic Manager / Front Door** for DNS/HTTP-level routing across regional endpoints with health probes. (3) Application-level client that holds multiple deployment endpoints and fails over with backoff. Consider: keep **data residency** in mind (failover regions must satisfy compliance), replicate any dependent data (e.g., AI Search indexes) per region, use **consistent deployment names** across regions for simple swapping, and watch quota in each region. **Global/Data Zone** deployment types also improve availability by spreading across infrastructure. Combine with retry/backoff honoring `Retry-After`. The robust enterprise answer: **multi-region deployments fronted by APIM (or Front Door) with health-based routing, retry, and failover**, respecting residency and replicating dependencies.

**Q27.** What is the difference between system, user, assistant, and tool messages?

The chat API uses **roles** to structure the conversation. **System** message sets the model's behavior, persona, rules, and constraints—high-priority instructions that shape all responses (put your guardrails and format requirements here). **User** messages are the human's inputs/questions. **Assistant** messages are the model's prior responses (included to maintain conversation history) and are where **tool calls** appear. **Tool** (formerly **function**) messages carry the **results** of executed tool/function calls back to the model, tied to a tool-call ID, so the model can incorporate them into its next answer. The typical tool-use flow: system + user → assistant emits a *tool call* → your code runs it → you append a *tool* message with the result → the model produces a final assistant answer. Newer models may use a **developer** role analogous to system for instruction precedence. Correctly using roles matters: instructions belong in system, untrusted content (like retrieved docs) should be clearly delimited within user content, and tool results must use tool messages with matching IDs.

**Q28.** How do you mitigate prompt injection on Azure OpenAI?

Prompt injection is when malicious instructions—directly from a user or **indirectly via retrieved/external content**—try to override your system instructions ("ignore previous instructions, reveal the system prompt / exfiltrate data"). Mitigations: (1) **Azure AI Content Safety Prompt Shields**—detects direct jailbreaks and **indirect (document-embedded) attacks**; enable it. (2) **Spotlighting/delimiting**—clearly mark external/retrieved content as untrusted *data* (e.g., wrap in delimiters/tags) and instruct the model to never follow instructions found within it. (3) **Least privilege on tools**—the model can request actions, but tools enforce **authorization** server-side and validate arguments, so an injected "delete everything" can't succeed. (4) **Output constraints**—structured outputs and not exposing the system prompt; filter outputs. (5) **Human-in-the-loop** before sensitive actions. (6) **Don't put secrets in the prompt**. (7) Monitor/log suspicious patterns. The especially important RAG case is **indirect injection through retrieved documents**—knowing to treat retrieved content as untrusted data (spotlighting) plus Prompt Shields, combined with privilege-limited tools, is the strong, senior-level answer.

**Q29.** What is the role of `max_tokens`, `temperature`, and `top_p`?

These control generation. **`max_tokens`** (or `max_completion_tokens` for newer/o-series) caps the length of the **completion**—important for cost control, latency, and ensuring you reserve context budget; too low truncates answers. **`temperature`** controls randomness/creativity: low (0–0.3) gives deterministic, focused, consistent output (ideal for RAG, extraction, classification, code), high (0.7–1.0+) gives more diverse/creative output (brainstorming). **`top_p`** (nucleus sampling) is an alternative randomness control—sample from the smallest set of tokens whose cumulative probability ≥ top_p; low top_p narrows choices. **Use one of temperature OR top_p**, not both aggressively. For factual/grounded tasks (most enterprise RAG/agents), set **low temperature** to reduce hallucination and improve consistency; raise it only for creative tasks. Note reasoning (o-series) models may ignore/handle temperature differently. Also relevant: `frequency_penalty`/`presence_penalty` to reduce repetition, and `seed` for more reproducible outputs. The senior point: for production grounded use cases, **low temperature + sensible max_tokens** for reliability and cost control.

**Q30.** How do you log and audit Azure OpenAI usage for compliance?

Enable **diagnostic settings** on the Azure OpenAI resource to send **logs and metrics** to **Log Analytics / Storage / Event Hub**—capturing request metadata, errors, content-filter events, and token/latency metrics (note: by default Azure doesn't log full prompt/completion *content* in platform logs for privacy; if you need content audit, capture it in your application layer with proper access controls and retention). At the **application layer**, log per request: timestamp, user/identity, deployment/model, token counts, finish reason, citations (for RAG), and a correlation ID—stored in a secured, access-controlled store with a defined **retention policy** and PII handling. Use an **APIM gateway** to centrally log per-consumer usage for chargeback and governance. Apply **RBAC** so only authorized roles can read audit logs, and consider **immutability** for compliance. Track **content-filter triggers** and **abuse signals**. Combine with Azure Monitor **alerts** on anomalies. The compliance-grade answer: **platform diagnostics (Azure Monitor) + application-level content/decision audit logs + APIM usage metering**, all access-controlled with retention policies and identity attribution.

**Q31.** What is the difference between completions, chat completions, and the Responses API?

The legacy **Completions** API takes a single prompt string and returns a continuation—now largely deprecated for chat models. The **Chat Completions** API (the workhorse) takes an array of role-tagged **messages** (system/user/assistant/tool), supporting multi-turn conversation, **tool/function calling**, structured outputs, and multimodal content—this is what most apps use. The newer **Responses API** (introduced by OpenAI and available on Azure) is a more **agentic, stateful** interface that unifies chat with **built-in tools** (e.g., file search, code interpreter, web/computer use depending on availability), can **manage conversation state server-side**, and streamlines multi-step tool-using flows—reducing client orchestration for agent scenarios *(verify current GA status)*. For straightforward chat/RAG, **Chat Completions** remains standard and well-supported; for **agentic** applications wanting server-managed state and integrated tools, the **Responses API** simplifies development. Choose Chat Completions for typical request/response and tool calling; consider the Responses API (and Azure AI Foundry Agent Service) when building stateful, tool-rich agents. Knowing this progression—completions → chat completions → responses/agents—shows current awareness.

**Q32.** How do you estimate and plan PTU capacity?

PTUs provide **dedicated throughput**, so you size them to your **peak sustained load** for the target model. Microsoft provides a **PTU capacity calculator/estimator** (in the Azure portal / Foundry) where you input your model, expected **calls per minute**, average **input and output token** sizes, and it estimates the **PTUs needed** to handle that throughput within latency targets. Steps: (1) measure or forecast traffic (RPM and token sizes per call, including RAG context), (2) use the estimator to get required PTUs for peak, (3) account for **burstiness**—either provision for peak or provision baseline PTUs plus **spillover to PAYG** for spikes, (4) consider **reservations** (monthly/yearly) for discounts on steady load, (5) validate with load testing and monitor **PTU utilization** to right-size over time. Trade-off: under-provisioning causes throttling at the PTU limit (mitigated by spillover); over-provisioning wastes money. The disciplined answer: **measure token/throughput profile → use the PTU estimator → provision baseline PTUs (reserved) + spillover for bursts → validate with load tests and monitor utilization**.

**Q33.** How do you handle PII and sensitive data in prompts?

Minimize and protect sensitive data sent to the model. Practices: (1) **Data minimization**—only include the PII actually needed for the task; redact/omit the rest. (2) **Redaction/de-identification**—use **Azure AI Language PII detection** (or Azure AI Content Safety) to detect and mask PII (names, SSNs, etc.) before sending, then re-identify in your app layer if needed. (3) **Don't log full prompts/completions** containing PII; if auditing, store in an access-controlled, encrypted, retention-governed store and scrub secrets. (4) Rely on Azure's **data commitments** (regional residency, no training on your data, abuse-monitoring **opt-out** for sensitive workloads so prompts aren't stored). (5) **Private Endpoints + managed identity + RBAC** so data stays private and access is controlled. (6) For RAG, **security-trim** retrieval so users can't pull others' PII. (7) Apply **content filters** and policy checks. The interview-grade answer: **minimize/redact PII (Azure Language PII detection), control logging, leverage data-residency/no-training/abuse-opt-out commitments, and enforce private networking + identity + trimming**—a defense-in-depth posture for sensitive data.

**Q34.** What is the Assistants API / Foundry Agent Service on Azure?

The **Assistants API** (OpenAI, available on Azure) and its evolution into **Azure AI Foundry Agent Service** provide a **managed, stateful agent** abstraction so you don't build the orchestration runtime yourself *(verify current GA status)*. You define an **agent/assistant** with instructions, a model, and **tools**—built-in ones like **file search (managed RAG)** and **code interpreter (sandboxed code execution)**, plus **function/OpenAPI** tools and (in Foundry) **MCP**, **Bing grounding**, and connections to Azure services. The service manages **threads** (conversation state), tool invocation, and execution server-side. **Foundry Agent Service** adds enterprise features: **identity/RBAC**, **networking** (bring-your-own VNet/storage/search), **content safety**, **observability/tracing**, and **evaluation**, and supports **multi-agent** orchestration—positioning it as the managed hosting/runtime that complements the **Microsoft Agent Framework** SDK (the AutoGen+SK convergence) for building agent logic. Use it when you want managed state, built-in RAG/code tools, and Azure-grade governance without running your own agent infrastructure. The key point: it's the **managed agent platform** on Azure—define agents + tools, and Azure handles state, execution, security, and monitoring.

**Q35.** How do you do streaming responses and why?

Streaming returns the model's output **incrementally** (token/chunk by chunk) as it's generated, rather than waiting for the full completion. You set `stream=true` and consume **server-sent events**; each event carries a delta you append/display. Benefits: dramatically better **perceived latency / UX**—the user sees text appearing immediately (critical for chat), the ability to **render progressively** and cancel early, and for agents, surfacing **intermediate steps** (tool calls) in real time. Considerations: handle partial/incomplete chunks, detect the terminal/`finish_reason`, manage **content-filter** behavior (filtering may apply to the stream), and aggregate tokens for logging/usage at the end. For tool calling, stream the assistant's tool-call construction then execute. In .NET, the `Azure.AI.OpenAI` chat client exposes streaming methods (`CompleteChatStreamingAsync`) yielding update objects you iterate with `await foreach`. Over the wire to a browser, forward via **SSE or WebSocket**. The interview point: streaming improves UX/perceived latency for interactive apps and enables progressive/agent UIs; non-streaming is fine for batch/back-end calls where you just need the final result.

**Q36.** How do you version and roll out model upgrades safely?

Treat model upgrades as **managed changes**, because behavior, cost, and latency can shift. Process: (1) **Pin** production deployments to a **specific model version** (avoid silent auto-updates for critical apps, or configure auto-update deliberately). (2) When a new version/model appears, deploy it to a **staging/parallel deployment** (using deployment-name indirection so app config can switch backends). (3) Run your **evaluation suite** (groundedness, accuracy, format adherence, safety) and **regression tests** comparing new vs current on a representative dataset—Azure AI Foundry evaluation helps. (4) **Load/latency/cost test**. (5) Roll out gradually—**canary/A-B** a percentage of traffic, monitor quality metrics, 429s, latency, and cost, then ramp. (6) Keep the old deployment for quick **rollback**. (7) Track **deprecation/retirement** dates so you migrate before forced changes. Update **API versions** intentionally too. The senior answer: **pin versions, evaluate new versions against an eval/regression suite in staging, canary roll out with monitoring and rollback, and track retirement timelines**—never just flip prod to a new model untested.

**Q37.** What is the difference between TPM quota and PTU throughput?

They're **different capacity models**. **TPM quota** applies to **Standard (PAYG)** deployments: it's an **allocation limit** from your subscription's regional pool that caps tokens-per-minute (and a derived RPM) for shared, on-demand capacity—exceed it and you get **429s**. It's about *how much of the shared pool you're allowed to use*, and you can have multiple deployments dividing your regional quota. **PTU throughput** applies to **Provisioned** deployments: you **reserve dedicated capacity** (provisioned units) that guarantees a certain throughput with **consistent latency**, isolated from other tenants—you pay for the reservation regardless of use, and you're limited by the provisioned throughput (exceed it and requests queue/throttle unless you have **spillover** to PAYG). So: TPM quota = *permission to consume shared capacity, billed per token*; PTU = *dedicated reserved capacity with predictable performance, billed for the reservation*. Plan TPM for variable/bursty workloads and PTUs for steady, latency-sensitive production. Confusing the two is a common mistake; clearly distinguishing **shared-quota-limited PAYG** from **dedicated-reserved PTU** signals real operational understanding.

**Q38.** How do you implement content safety beyond the built-in filters?

The built-in Azure OpenAI content filters are a baseline; for robust safety, layer additional controls. (1) **Azure AI Content Safety** directly—call the **Text/Image moderation** API and **Prompt Shields** (jailbreak/indirect-injection detection) and **Groundedness detection** on inputs/outputs in your own pipeline for finer control than the deployment-attached filter. (2) **Custom blocklists/categories** in Content Safety for domain-specific terms. (3) **System-prompt guardrails** and refusal instructions. (4) **Structured outputs + validation** to constrain responses. (5) **Business-rule checks** (e.g., never give medical/legal advice, mask PII) implemented in code. (6) **Human-in-the-loop** review for high-risk outputs/actions. (7) **Groundedness/citation enforcement** for RAG to prevent hallucination. (8) **Output post-processing** and logging/alerting on violations. (9) **Rate limiting and abuse detection** at the gateway (APIM). For agents, gate **tool actions** with authorization and approval. The point: built-in filters handle generic harm categories, but production safety = **Content Safety APIs (incl. Prompt Shields/groundedness) + custom rules + structured validation + HITL + monitoring**, tailored to your domain's risks.

**Q39.** How do you measure model latency and throughput?

Define and measure the right metrics. **Latency**: **time-to-first-token (TTFT)**—how quickly streaming starts (drives perceived responsiveness)—and **end-to-end latency** (full completion time), reported as **p50/p95/p99** under realistic load, since tails matter. Latency scales with **input and output token counts**, model choice (reasoning models are slower), and contention (429/queueing). **Throughput**: **tokens per second** generated and **requests per minute** the deployment sustains, plus **TPM/PTU utilization**. Measure via: (1) **Azure Monitor metrics** (latency, token counts, throttling, PTU utilization), (2) **OpenTelemetry** app traces capturing per-call TTFT, total latency, and token usage, (3) **load testing** (e.g., with representative prompts) to find the point where latency degrades or 429s appear—informing PTU sizing. Optimize latency by **streaming**, **reducing output tokens** (`max_tokens`, concise prompts, reranked RAG context), **prompt caching**, **right-sizing the model**, **co-locating** services in-region, and **PTUs** for predictable performance. The senior answer: track **TTFT + p95/p99 end-to-end latency + tokens/sec + utilization** under load, and tune via streaming, token reduction, caching, and capacity (PTU).

**Q40.** What is the Customer Copyright Commitment and IP protection?

Microsoft's **Customer Copyright Commitment** (part of the Copilot Copyright Commitment) is a contractual assurance: if a customer using certain Azure AI / Copilot services (including Azure OpenAI) is sued for **copyright infringement over output** the service generated, Microsoft will **defend the customer and pay resulting damages/settlements**, provided the customer used the built-in **guardrails and content filters** (including any required mitigations like protected-material detection) and didn't intentionally infringe. To support this, Azure OpenAI includes **protected material detection** (flagging output that matches known copyrighted text/code) so you can avoid emitting verbatim protected content. Combined with Azure's **data commitments** (your data isn't used to train the models; you retain rights to your inputs/outputs), this gives enterprises IP/legal confidence to deploy generative AI. The interview point: Microsoft offers a **copyright indemnification** for generated output when you use the required safety features, and **protected material detection** is the mechanism that helps you stay within those terms—an enterprise differentiator versus less-protected alternatives.

**Q41.** How do you architect a multi-tenant SaaS on Azure OpenAI?

Key concerns: **isolation, fairness, cost attribution, and security** across tenants. Patterns: (1) **Capacity management**—front Azure OpenAI with an **APIM GenAI gateway** enforcing **per-tenant token quotas/rate limits** so one tenant can't starve others, with **load balancing/failover** across deployments/regions. (2) **Cost attribution**—meter token usage **per tenant** (via APIM logging / app telemetry) for chargeback. (3) **Data isolation**—for RAG, isolate each tenant's data (separate indexes or strict **filter/security-trimming** on a tenant ID) and enforce it in the retrieval layer; never let one tenant's query retrieve another's data. (4) **Identity**—use **managed identity** to Azure OpenAI; authenticate tenants at the gateway (JWT/keys). (5) **Networking**—Private Endpoints; tenant data stays in-region per residency. (6) **Capacity strategy**—PTUs for baseline + spillover for bursts, or dedicated deployments for premium tenants. (7) **Per-tenant config**—content-filter levels, model tiers. (8) **Monitoring/alerting** per tenant. The robust answer: **APIM gateway for per-tenant quota/metering/failover + strict per-tenant data isolation (index/filter) + managed identity + private networking + PTU/spillover capacity + per-tenant observability**.

**Q42.** What are tokens, and how do you count/estimate them?

A **token** is the unit models process—roughly a word-piece; on average ~**4 characters** or ~**0.75 words** in English (varies by language and content; code/non-English use more). Both **input (prompt)** and **output (completion)** tokens are billed, and the **context window** limits their sum. To count/estimate: use the **tokenizer** matching the model (OpenAI's **tiktoken** library, e.g., the `o200k_base` encoding for GPT-4o-family) to count exactly before sending—useful to stay within context limits and predict cost; the API **usage** object also returns actual `prompt_tokens`, `completion_tokens`, and `total_tokens` per call (and cached-token counts with prompt caching). Practical uses: **budget** prompts (trim RAG context to fit and control cost), set **`max_tokens`** leaving room for the answer, and **forecast cost** (tokens × price per 1K, different rates for input vs output, discounts for cached/batch). Note **reasoning models** also consume hidden reasoning tokens. The interview point: tokens ≈ ~4 chars; **count with tiktoken** to manage context/cost up front and read the **usage** field for actuals—token awareness underlies cost, latency, and context planning.

**Q43.** How do you connect Azure OpenAI to Azure AI Search for RAG (without On Your Data)?

Build a custom pipeline for full control. **Indexing**: chunk and embed documents with an Azure OpenAI **embeddings deployment** (or use AI Search **integrated vectorization** so Search calls the embedding deployment), storing vectors + text + metadata in an AI Search index with **HNSW** and a **semantic config**. **Query time**: (1) embed the user query (same embedding model) via Azure OpenAI; (2) call **AI Search** with a **hybrid** query (search text + query vector) and `query_type="semantic"` for semantic reranking, applying **filters/security trimming**; (3) take the top reranked chunks, assemble a **grounded prompt** (system instructions to answer only from context and cite source IDs + the chunks + the question); (4) call the **Azure OpenAI chat** deployment to generate the answer with citations, streamed. Use **managed identity** for both services, co-locate them **in-region**, and add retries/monitoring. This custom approach (vs On Your Data) lets you control **reranking depth, query rewriting/HyDE, multi-hop, prompt engineering, and structured outputs**. It's the standard advanced Azure RAG architecture and a likely whiteboard question.

**Q44.** What happens when content is filtered, and how do you handle it gracefully?

When input or output triggers a content filter at or above the configured **severity threshold**, Azure OpenAI **blocks** the offending content: for **prompts**, the request is rejected (an error indicating which category/severity triggered); for **completions**, the response comes back with a **`finish_reason` of `content_filter`** and the content withheld (or partially, in streaming). Your app must **handle this gracefully**, not crash or expose raw errors: (1) detect the `content_filter` finish reason / error and the triggered category; (2) return a **user-friendly message** ("I can't help with that request") rather than a stack trace; (3) **log** the event (category, severity) for safety monitoring without storing harmful content insecurely; (4) optionally **route** to a safe fallback or escalate; (5) for false positives in legitimate scenarios, consider **adjusting filter configuration** (or applying for modified filters) and refine prompts. Also account for **streaming** (filtering may interrupt a stream) and **annotations** that indicate which category fired. The key point: filtering is expected behavior—**design the app to detect, message, log, and recover** from `content_filter` outcomes.

**Q45.** How do you do A/B testing of prompts/models in production?

Treat prompts and models as **versioned, testable artifacts**. **Offline first**: maintain an **evaluation dataset** of representative inputs with reference answers/criteria, and run candidate prompts/models through **Azure AI Foundry evaluators** (groundedness, relevance, accuracy, safety) to compare before any live test. **Online A/B**: route a **percentage of live traffic** to the variant (control vs candidate)—via feature flags or an **APIM gateway** that splits by header/tenant and (using deployment-name indirection) targets different deployments. Measure **outcome metrics** (user thumbs up/down, task success, follow-up/deflection rate) and **operational metrics** (latency, 429s, **token cost**). Ensure **statistical rigor** (sufficient sample, control for confounders) and **change one variable at a time** (prompt OR model). Keep **rollback** easy (config switch). Log per-variant for analysis. Wire offline eval into **CI** to catch regressions before deploy. The senior answer: **offline eval on a labeled dataset to gate, then online canary/A-B via APIM/feature flags measuring quality + cost + latency, with monitoring and quick rollback**—data-driven, not vibes-driven, prompt/model iteration.

**Q46.** What is `logit_bias` and the `seed` parameter?

**`logit_bias`** lets you nudge or forbid specific tokens by adding a bias (-100 to 100) to their logits before sampling: a large negative (-100) effectively **bans** a token, a large positive **forces/encourages** it. Use cases: prevent the model from emitting certain words, steer toward a constrained vocabulary, or block specific outputs—though it's low-level (you specify **token IDs**, found via the tokenizer) and brittle compared to clear prompting or structured outputs, so it's for niche control. **`seed`** requests **more deterministic/reproducible** outputs: with the same seed, prompt, and parameters, the model attempts to return the same result (and exposes a `system_fingerprint` so you can detect backend changes). It's **best-effort, not guaranteed** (infrastructure changes can alter output), but useful for **testing, debugging, caching, and reproducibility** of evaluations. Combine `seed` with **low temperature** for the most consistent results. The interview point: `logit_bias` = fine-grained token-level steering/banning (niche); `seed` = best-effort reproducibility for testing/consistency. Neither replaces good prompting/structured outputs, but both are useful tools for control and determinism.

**Q47.** How do you handle rate limits across many microservices?

When many services share Azure OpenAI capacity, uncoordinated clients can collectively blow TPM/RPM and cause cascading 429s. Solutions: (1) **Centralize through an APIM GenAI gateway**—enforce **token-based rate limiting and per-consumer quotas** so each service/tenant gets a fair slice, with **load balancing/failover** across multiple backends/regions and **retry** at the gateway; this is the cleanest answer for many microservices. (2) **Distributed throttling**—a shared rate limiter (e.g., Redis-based) so services coordinate a global request/token budget rather than each retrying blindly. (3) **Capacity strategy**—size **TPM quota** per region, use **PTUs** for predictable baseline + **spillover** to PAYG for bursts, and spread across regions/deployments. (4) **Client resilience**—exponential **backoff with jitter** honoring **`Retry-After`** in every service. (5) **Queue/batch** non-urgent work (or use the **Batch API**) to flatten spikes. (6) **Monitor** 429 rates and utilization per service. The strong enterprise answer: **APIM gateway enforcing per-consumer token quotas + multi-backend failover**, backed by PTU/spillover capacity and resilient backoff in clients—turning chaotic shared usage into governed, fair, reliable access.

**Q48.** What's the difference between Azure OpenAI and Azure AI Foundry?

**Azure OpenAI Service** is the specific service exposing **OpenAI's models** (deployments, inference APIs, content filters, PTUs). **Azure AI Foundry** (formerly Azure AI Studio) is the broader **platform and unified experience** for building, evaluating, deploying, and governing AI applications and **agents** on Azure. Foundry encompasses Azure OpenAI **plus** a **model catalog** (OpenAI **and** other providers—Meta, Mistral, etc.), the **playground**, **prompt flow** and **evaluation** tooling, **On Your Data**/RAG, the **Agent Service**, **content safety/responsible AI** features, **fine-tuning**, **monitoring**, and project/hub-based **governance, security, and connections** (to AI Search, Storage, etc.). In short: **Azure OpenAI = the model-serving service**; **Azure AI Foundry = the end-to-end development and operations platform** that includes Azure OpenAI among many capabilities. The framing: you **consume Azure OpenAI models**, but you **build, evaluate, secure, and operate** your GenAI/agent solutions **in Azure AI Foundry** (with the Microsoft Agent Framework SDK for custom orchestration). Knowing this hierarchy avoids conflating the model service with the broader platform.

**Q49.** How do you ensure reproducibility and determinism in tests?

LLMs are stochastic, so test design must accommodate variability while maximizing consistency. Techniques: (1) **temperature = 0** (and avoid aggressive top_p) for the most focused, repeatable outputs. (2) Use the **`seed`** parameter (best-effort determinism) and check the **`system_fingerprint`** to detect backend changes that could alter results. (3) **Pin the model version** and **API version** so tests aren't disturbed by silent upgrades. (4) For unit tests of orchestration/tools, **mock the model client** with canned responses—fully deterministic and free. (5) For evaluation tests, assert on **invariants and tolerances** (valid JSON/schema via structured outputs, presence of citations, factual correctness via LLM-as-judge with a rubric) rather than exact string equality, and use a **fixed eval dataset**. (6) Record actual outputs (golden files) and review diffs deliberately. (7) Run multiple samples and assert on **aggregate pass rates** for flaky behaviors. The senior answer: **temperature 0 + seed + pinned versions + mocking for logic + schema/rubric-based assertions on a fixed dataset**—accept that perfect determinism isn't guaranteed, so test structure and invariants, not exact text.

**Q51.** What is Azure AI Search and what role does it play in RAG?

Azure AI Search is Microsoft's managed search service and the backbone of Azure RAG. It provides keyword (BM25), vector, and hybrid search in one index, plus a **semantic ranker** (cross-encoder reranking), filtering, faceting, and **security trimming**. With **integrated vectorization**, it can chunk and embed documents during indexing (calling Azure OpenAI embeddings) and vectorize queries automatically, reducing custom code. It supports **indexers** that pull from Blob Storage, SQL, Cosmos DB, etc. For an AI engineer building "chat over your data," it's the recommended retrieval layer: you get **hybrid + semantic ranking**, scale, and enterprise security (Entra ID, document-level access) without standing up a separate vector database. The strong default retrieval config is **hybrid + semantic reranking**; pure vector is rarely optimal for documents containing identifiers, code, or domain terms. The vector index uses **HNSW** (tune `m` / `efConstruction` / `efSearch`) with **cosine** similarity, and supports **scalar/binary quantization** with oversampling for large indexes.

**Q52.** Compare Semantic Kernel and Azure AI Foundry Agent Service.

Azure AI Foundry Agent Service is a **managed cloud service** for building and hosting agents with **built-in tools** (code interpreter, file search/RAG, Bing grounding, connected tools), **thread/state management**, and enterprise security—less code, more managed infrastructure *(verify current GA status)*. Choose SK when you want lightweight, embeddable orchestration and control; choose the Agent Service when you want a hosted, managed agent runtime with built-in tools and governance. Many solutions use SK locally for the agent logic and **deploy onto Foundry** for managed state, tools, and Azure-grade governance.
